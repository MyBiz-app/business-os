## מה אני צריך ממך (פעולות, מתי שנוח)

1. ✅ **תבניות המייל ב-Supabase**: מוגדרות (נבדק ב-10.10, זהות ל-`supabase/templates/`).
2. ✅ **כתובות החזרה ב-Supabase**: מוגדרות (Site URL ו-`https://business-os-alpha-drab.vercel.app/**`).
3. ✅ **האפליקציות בטלפון (Expo, בחינם)**: פורסמו (10.10) ופתוחות בדפדפן: `mybiz-client-app.vercel.app`, `mybiz-business-app.vercel.app`, `mybiz-staff-app.vercel.app`. אפשר להוסיף למסך הבית. עדכון אחרי שינוי: Actions ← Deploy the Expo apps to the web ← Run workflow.
4. **התחברות עם Google** (כ-10 דקות):
   1. ב-[Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials) יוצרים OAuth client מסוג Web application.
   2. ב-Authorized redirect URIs מדביקים את ה-Callback URL שמופיע ב-[Supabase → Authentication → Sign In / Providers → Google](https://supabase.com/dashboard/project/_/auth/providers). הכתובת נראית כך: `https://<project>.supabase.co/auth/v1/callback`.
   3. מעתיקים את ה-Client ID וה-Client Secret ל-Supabase ומפעילים את Google. הכפתור יופיע באתר לבד, תוך 5 דקות לכל היותר.
4. **התחברות עם Apple** (אופציונלי, אפשר בהמשך). הכפתור כבר באתר, מושבת עם תווית "בקרוב", ויופעל רק אחרי השלבים האלה. צריך חשבון [Apple Developer](https://developer.apple.com/programs/) בתשלום שנתי:
   1. ב-Apple Developer → Identifiers יוצרים App ID (עם Sign in with Apple) ו-Services ID (זה ה-Client ID).
   2. ב-Services ID מגדירים את הדומיין ואת ה-Return URL: ה-Callback של [Supabase → Authentication → Sign In / Providers → Apple](https://supabase.com/dashboard/project/_/auth/providers).
   3. יוצרים Key עם Sign in with Apple ומורידים את קובץ ה-`.p8` (אפשר להוריד פעם אחת בלבד).
   4. ב-Supabase מדביקים את ה-Services ID וה-Secret Key (JWT שנוצר מה-`.p8`, [המדריך של Supabase](https://supabase.com/docs/guides/auth/social-login/auth-apple); הוא פג כל 6 חודשים, צריך לחדש) ומפעילים את Apple.
   5. ב-Vercel מגדירים משתנה סביבה `AUTH_APPLE_ENABLED=true` ועושים deploy. הכפתור יהפוך לפעיל. את ה-`.p8` לא שולחים לי.
5. **להחליף את הסיסמאות הזמניות** של חשבונות הדמו. **לא לשלוח לי** את הסיסמה החדשה.
6. **החלטות פתוחות:** [#46](https://github.com/MyBiz-app/business-os/issues/46) ספק סליקה (ממנו יגיעו גם Apple Pay ו-Google Pay), [#47](https://github.com/MyBiz-app/business-os/issues/47) ספק חשבוניות, [#36](https://github.com/MyBiz-app/business-os/issues/36) שם המותג. הספקים יחוברו כשהעסק יתחיל לפעול (X21), והשם הוא MyBiz בינתיים.
7. **דוח התיקונים והשיפורים** שלך, לפני העלייה לאוויר.
8. **להדליק אחסון קבצים (2 דקות, מתי שנוח לפני העלייה לאוויר).** ב-[Supabase → Project Settings → API Keys](https://supabase.com/dashboard/project/mywfwzdrlbpxeheszasd/settings/api-keys) מעתיקים את ה-secret key, וב-Render (שירות ה-API ← Environment) מוסיפים `API_STORAGE_PROVIDER` = `supabase` ו-`API_STORAGE_SETTINGS` = `{"url": "https://mywfwzdrlbpxeheszasd.supabase.co", "service_key": "<המפתח הסודי>"}`. **לא לשלוח לי** את המפתח.
9. **להדליק ניטור שגיאות (10 דקות, לפני העלייה לאוויר).** פותחים חשבון [Sentry](https://sentry.io) חינמי ושלושה פרויקטים (Python, Next.js, React Native) ומגדירים את שלושת ה-DSN לפי `docs/guides/monitoring.md`. אפשר להוסיף גם ניטור זמינות חיצוני חינמי על `/health/ready`.
10. **משימות AI מתוזמנות, בדיקה כל 10 דקות (2 דקות, כשנוח).** ב-GitHub: Settings ← Secrets and variables ← Actions ← New repository secret, בשם `API_INTERNAL_TOKEN`, והדביקו את אותו ערך שמוגדר כ-`API_INTERNAL_TOKEN` ב-Render. עד אז משימות רצות רק בלחיצה על "הרצה עכשיו".

12. **הדיפלוי היחיד ל-Vercel (כשהכול גמור).** מיזוג ל-main כבר לא מפרסם כלום (ב-Vercel Hobby יש מגבלה של 100 דיפלויים ביום). כשהעבודה גמורה: GitHub ← Actions ← להריץ **"Deploy web to Vercel"** (האתר וה-CRM, `business-os-alpha-drab.vercel.app`), ואחריו **"Deploy the Expo app to the web (Vercel)"** עם app = `all` (`mybiz-client-app.vercel.app`). שניהם ידניים בלבד. קודם להריץ מיגרציות עם "Migrate staging database". ## בעבודה

- **שיעור פרטי תופס מאמן ומגרש יחד (פרוסה C4 של הקטגוריות, מיגרציה 0157).** שירות יכול לומר עכשיו שהוא צריך חדר (`needs_resource`, לשירותי תור בעסק, למשל שיעור טניס פרטי על מגרש או טיפול בחדר טיפולים); החדרים שמשרתים אותו נקבעים ב־`PUT /services/{id}/rooms` הקיים (נוסף גם `GET`). זמנים פנויים הם החפיפה: המאמן פנוי ובתוך שעות העבודה שלו, וחדר מקושר פתוח ופנוי, וכל זמן מציין באיזה מגרש ייערך. הזמנה תופסת את שניהם בבת אחת, והחדר נבחר על ידי הלקוח או, אם לא נבחר, הראשון הפנוי; שניים שלוחצים "הזמן" באותו רגע אף פעם לא יקבלו אותו מאמן או אותו מגרש (נעילות ואילוץ במסד). שיעור חוסם השכרת מגרש באותה שעה והשכרה חוסמת את השיעור; ביטול משחרר את שניהם; והמסד מסרב לשיעור של שירות כזה בלי מגרש בכל דרך שהיא (כולל רשימת המתנה). עוד אין שינוי במסך; שירותים שלא סימנו את הדגל עובדים כמו קודם.
- **פעילויות במסד הנתונים (פרוסה C2 של הקטגוריות, מיגרציה 0156).** לעסק יש עכשיו פעילויות (`tenant_activities`: מה הוא מציע, וכל אחת זוכרת מאיזה סוג עסק באה; כיבוי לא מוחק) ולכל סניף רשימה משלו (`location_activities`; סניף חדש מתחיל עם כל פעילויות העסק, בעזרת טריגר במסד). למגרשים וחדרים נוספו סוג משאב ותכונות, לשירות נוסף שיוך לפעילות, וטבלת `tenant_profile` מחכה לתשובות ההרשמה (C7). עסקים קיימים מתמלאים לפי התעשייה שלהם; עסק שהתעשייה שלו היא קטגוריה שלמה (כמו "כושר") לא מקבל פעילויות התחלתיות עד שהבעלים יבחר. API: `GET/PUT /activities` ו־`GET/PUT /locations/{id}/activities`. סניף יכול להיות מכל תעשייה בקטלוג ולא רק מהקטגוריה של העסק, כך שעסק אחד יכול לשלב מועדון טניס, חדר כושר וחדר פיזיותרפיה. עוד אין שינוי במסך.
- **קטלוג 2: סוגי עסק, פעילויות ומודלי שירות (פרוסה C1 של הקטגוריות, בלי מיגרציה ובלי מסך).** לקטלוג התעשיות יש צורה חדשה לצד הקיימת: 12 תחומים, 76 סוגי עסק (כ־25 חדשים: מועדון טניס ומועדון פאדל נפרדים במקום "פאדל וטניס", בית ספר לשחייה, חדר בריחה, בית ספר לנהיגה, קעקועים, מנעולן, פנסיון לחיות ועוד), 28 סוגי משאבים (טניס, פאדל, קט־רגל, כדורסל, רפורמר, חדר טיפולים...) ושמונה מודלי שירות. לכל סוג: שמות ושמות נרדפים בעברית ובאנגלית, פעילויות ומשאבים התחלתיים, 2-4 שאלות חכמות להרשמה, שילובים נפוצים והמפתחות הישנים שהוא מחליף. חיפוש מוצא סוג לפי מה שהבעלים מקליד ("טניס", "מגרש טניס באשדוד", "tenis"). הקטלוג מיוצא לאתר, לאפליקציות ול־API, ובדיקות מוודאות שכל הפניה תקינה ושכל סוג נמצא לפי שמו. עוד שום דבר לא קורא ממנו: טבלאות הפעילויות הן פרוסה C2.

- סבב 7, פרוסה R11 (חלונות להצעות, אירועים ומסמכי כספים, בלי מיגרציה): הצעה חדשה, הצעה קיימת, מסמך חדש (חשבונית, קבלה, זיכוי) וחשבונית או קבלה שמורות נפתחים כחלון מעל הרשימה (אותו חריץ `@modal` מ-R10); רענון או קישור ששלחו עדיין פותחים את העמוד הרגיל. עמוד ההצעות נקרא עכשיו "הצעות ואירועים" (בתפריט, בתחום האירועים): סלייסר בין הצעות לאירועים, תצוגת האירועים היא לוח חודשי ורשימה, מספרים בראש (טיוטות, ממתינות, אושרו, שיעור סגירה; "אושרו החודש" דורש תאריך אישור ברשימת ההצעות, לא נוסף), ועמוד ריק שמלמד שלושה צעדים עם כפתור לדוגמה ממולאת. `/events` מפנה אליו. בנוסף תוקן לוח השבוע האיטי: Postgres קימפל (JIT) שאילתות קטנות כי פונקציות ההרשאה לפי שורה גורמות לכל תוכנית להיראות יקרה; עכשיו בקשות מכבות JIT (שבוע בלוח 0.65 שנ' ל-0.03, `/attention` מ-0.67 ל-0.18 על בסיס עם 2,000 לקוחות).
- סבב 7, פרוסה R1 (ערכת רכיבים, בלי מיגרציה): רכיבים משותפים חדשים ב-`apps/web/src/components/ui` לשאר הסבב: `Modal` (חלון כמעט במסך מלא מעל העמוד, בטלפון עולה מלמטה; Esc, X ולחיצה על הרקע סוגרים, ושואל "לצאת בלי לשמור?" כשיש שינויים), `CollapsibleSection` (חץ בתחילת השורה, המצב נשמר), `SegmentedControl` עם גלולה שזזה ו-`ContentSwap` (החלפת תוכן רכה), ומצבי טעינה (`LoadingDots`, `ProgressBar`, `PendingContent`). עדיין אף מסך לא משתמש בהם; הפרוסות הבאות מעבירות מסכים. הכללים ב-`docs/guides/design-system.md`.
- סבב 7, פרוסה R12 (תפריט צד עם תתי פריטים, בלי מיגרציה): תפריט הצד ב-CRM מקבץ דפים קשורים תחת פריט אב עם חץ (אנשים, משמרות, שכר, לקוחות, הזמנות אתר, צוות ה-AI). פריט האב נפתח בלחיצה וזוכר את מצבו, תתי הפריטים גוללים בעדינות אל הקטע שלהם, ומעקב גלילה מדגיש את הקטע שקוראים. התפריט עובד במקלדת ובטלפון.
- סבב 7, פרוסה R14 (פרופיל בתוך מסגרת ה-CRM, בלי מיגרציה): הפרופיל (`/account`) נפתח עכשיו בתוך מסגרת ה-CRM (תפריט צד, בורר סניף, בועת AI) לכל מי שיש לו עסק, ולא נראה כמו אתר אחר. שמונת הכרטיסים הפכו לסעיפים מתקפלים (פרטים ראשון ופתוח, השאר כפי שהמשתמש השאיר, נשמר בדפדפן) עם תפריט סעיפים צף במסכים רחבים שפותח סעיף וגולל אליו. קישורים כמו `/account#security` פותחים את הסעיף הנכון. עסק סגור או מושעה, או אימות דו-שלבי חסר, משאירים את הדף במעטפת הרגילה כדי שיהיה תמיד אפשר לפתוח אותו.
- סבב 7, פרוסה R5 (כרטיס עובד ומספרים לחיצים, בלי מיגרציה): לכל עובד יש עכשיו כרטיס ב-`/team/[userId]` עם שש לשוניות בסלייסר נע: סקירה (פרטי קשר, סניפים, משמרות ושיעורים ב-14 הימים הקרובים, שעות החודש למי שמאשר שעות), העסקה ושכר (תיק השכר, מוטמע), זמינות (זמינות שבועית, שעות עבודה, חופשות), מסמכים (טופס 101, תאריך הודעה), AI (גישה וקרדיטים החודש) והרשאות (תפקיד ומה הוא מאפשר). לשונית מוצגת רק למי שמורשה לראות אותה (שכר ומסמכים דורשים `payroll.read`, AI דורש `ai.manage`). השמות ברשימת הצוות פותחים את הכרטיס, והדפים הישנים `/hours`, `/availability` ו-`/payroll` מפנים אליו. בלידים, בהצעות מחיר ובחשבוניות נוספו אריחי סיכום שהם קישורים אמיתיים לרשימה מסוננת בדיוק למה שהם סופרים (לידים: חדשים, נסגרו, המרה, מעקבים להיום; הצעות לפי סטטוס; מסמכים לפי סוג). באפליקציה, כפתורי הימים ב"היום" מציגים את מספר השיעורים, והמספרים ב"מספרים" לחיצים (לקוחות פעילים, חדשים ואי-הגעה פותחים את רשימת הלקוחות, נוכחות פותחת את "היום", הכנסות ותפוסה פותחות את הדוח באתר). הדשבורד והדוחות באתר הם פרוסה R4.
- סבב 7, פרוסה R4 (לוח מקושר וטווח תאריכים, בלי מיגרציה): כל כרטיסיית דשבורד היא קישור אמיתי לרשימה המתאימה באותה תקופה (הכנסות למכירות, לקוחות פעילים וחדשים ואי-הגעה לרשימת הלקוחות, נוכחות ללוח השיעורים, תפוסה לדוח "לפי שירות" ממוין לפי תפוסה), ושני הגרפים פותחים את השבוע של העמודה שנלחצה. בורר תקופה משותף (7, 30, 90 ימים או טווח חופשי עם החודש, החודש שעבר ומתחילת השנה) בדשבורד, בדוחות ובמכירות מחליף את הנתונים במקום: הדף נשאר איפה שהוא והמספרים הישנים מתעמעמים עם נקודות טעינה. מסנני לקוחות חדשים `joined_from` / `joined_to` ו-`no_show_from` / `no_show_to` ב-`GET /clients`; המכירות והייצוא ל-CSV מקבלים טווח חופשי; שורות בדוחות פותחות את לוח השיעורים מסונן לשירות או למדריך, וסניף פותח את הדשבורד של אותו סניף. רשימות תשומת הלב בדשבורד ירדו מכ-0.7 שנייה ל-0.12 בדמו עם 20,000 הזמנות: הביקור האחרון נלקח עכשיו מ-`checked_in_at` של ההזמנה במעבר אחד (צירוף ל-sessions עלה בדיקת RLS לכל הזמנה). לא בפרוסה: פרופיל עובד (R5), כרטיסי סיכום בלידים, הצעות וחשבוניות, וקישורי "היום" ו"מספרים" באפליקציה.
- סבב 7, פרוסה R3 (בלי קפיצה לראש הדף, שלדי טעינה, בלי מיגרציה): קישורי תקופה, חודש, עמוד וסינון נשארים במקום (`scroll={false}`, וכלל lint חדש `design-system/no-scroll-jump` שומר על זה), עמודי ה-CRM הכבדים (לקוחות, לידים, חשבוניות, לוח שיעורים, משמרות, מכירות, צוות, שכר, קבצים, AI) מציגים שלד באותו רוחב, וזוגות כפתורים (סוגי חשבוניות, סינון הצעות מחיר, תיבה, תצוגת לוח, טווח ותצוגת משמרות, מיון תוכן) משתמשים ב-`LinkSegmented` החדש: הגלולה זזה מיד ונקודות מופיעות בזמן טעינת הנתונים. הדשבורד והדוחות נשארו ל-R4.
- סבב 7, פרוסה R32 (מדיניות ביטולים ומנוי X בשבוע, מיגרציה 0138): העסק קובע בהגדרות, "הזמנות", את תנאי הביטול: עד כמה זמן לפני שיעור קבוצתי, שיעור אישי או תור, ומגרש או חדר מבטלים בחינם; האם ביטול מאוחר ואי-הגעה נחשבים כביקור שנוצל או רק נרשמים (קנס קיים במודל אבל נשאר כבוי עד שמדליקים תשלומים); ועצירה אופציונלית של הזמנות באפליקציה אחרי אי-הגעות חוזרות. משפט מתחת לטופס משתנה תוך כדי הבחירה. התנאים מתחילים מברירת המחדל של קטגוריית העסק (כושר, סטודיו וספורט: 6 שעות לשיעור קבוצתי ו-24 לשיעור אישי או מגרש; יופי וקליניקות: 24 שעות; אחרים: 2 ו-12 שעות, רק נרשם) וממתינים לאישור אחד, שהוא צעד חדש ברשימת ההקמה. לשירות ולמסלול אפשר תנאים משלהם, והספציפי גובר (מסלול, אחר כך שירות, אחר כך עסק). מסלול מנוי יכול להגביל ל-X ביקורים בשבוע או בחודש (למשל 2 בשבוע): ההזמנה בודקת את מכסת השבוע, וביטול מאוחר מוריד ביקור רק אם המדיניות קובעת כך. הלקוח רואה בכל הזמנה "ביטול חינם עד יום ב 13:00", ובביטול מאוחר חלון שאומר בדיוק מה יקרה ("השיעור עדיין ייחשב לך מתוך 2 הביקורים של השבוע"). מנהל (בעלים, מנהל, מנהל סניף, קבלה) יכול להחזיר ביקור מרשימת המשתתפים, עם סיבה חובה; הלקוח מקבל הודעה, נשמר מי ומתי, ובכרטיס הלקוח רואים כמה הוחזרו השנה. המדיניות גם מנוסחת ללקוחות בעברית ובאנגלית. ביטול המנוי עצמו לא חלק מהפרוסה הזו (חוק הגנת הצרכן; מומלץ לבדוק עם עורך דין).
- סבב 7, פרוסה R23 (הקפאה מהאפליקציה ומנוי מתחדש, מיגרציה 0135): למסלול מנוי אפשר להגדיר מחזור חיוב (חודשי, כל 3 חודשים, שנתי או מספר ימים) ו"מתחדש אוטומטית"; למנוי שנמכר יש תאריך חיוב הבא וסכום החיוב הבא (החיוב עצמו עדיין מדומה עד שמחברים ספק סליקה). לקוח מבקש הקפאה מהאפליקציה (הזמנות, "הקפאה" מתחת למסלול): בוחר ימים בלוח שנה, סיבה (נסיעה, מילואים, מחלה, הריון, אחר) והערה, ורואה בדיוק מה יקרה לפני השליחה (תאריך סיום חדש, החיוב הבא עובר מתאריך לתאריך, או זיכוי, דמי הקפאה, והסכום הבא). הבקשה מחכה למנהל הסניף: היא מופיעה בדשבורד ("בקשות הקפאה להחלטה"), בכרטיס הלקוח (לאשר הכל, לאשר עד יום מסוים, או לדחות עם הודעה) והלקוח מקבל עדכון. העסק קובע חוקים בהגדרות, "מנויים והקפאות": בקשות פתוחות או סגורות, הקפאה קצרה וארוכה ביותר, בנק ימי הקפאה שנתי ללקוח (הלקוח רואה כמה נשאר), הודעה מראש, דמי הקפאה, דחיית החיוב הבא או זיכוי, וסיבות שמאושרות אוטומטית. מנוי ששולם מראש מקבל הארכת תאריך סיום; מנוי מתחדש גם דוחה את החיוב הבא (ברירת מחדל) או מקבל זיכוי יחסי מעוגל לטובת הלקוח. "חזרתי מוקדם" (לקוח או מנהל) מסיים את ההקפאה אתמול ומחזיר את הימים שלא נוצלו, את החיוב שנדחה ואת הזיכוי; הקפאה שעוד לא התחילה נעלמת. אי אפשר להקפיא כרטיסייה. נוסף בהמשך (מיגרציה 0139): לקוח יכול לצרף לבקשה תמונה של אישור רפואי או צו (נשמרת במסמכים שלו, והמנהל פותח אותה מהבקשה), לסוכן שירות הלקוחות יש כלי `suggest_freeze` שרק מציע (מראה תאריך סיום חדש ואיך החיוב הבא זז, ואף פעם לא מקפיא), וברירות המחדל של החוקים עכשיו לפי החלטה 18.11 (בנק של 30 ימי הקפאה בשנה, עד 90 ימים לבקשה). לא נבנה: תהליך חידוש אוטומטי (מחכה לספק סליקה).
- סבב 7, פרוסה R6a (בועת ה-AI, בלי מיגרציה): הרשימה שנפתחת מכפתור ה-AI העגול מציגה כל סוכן כגלולה עם תמונה, שם ותפקיד (בטלפון נפתחת בלחיצה), לא חוזרת על הסוכן שכבר על הכפתור, ומתמלאת עד 5 לפי הרלוונטיות לעמוד. מפת עמוד לסוכן מגיעה עכשיו מהשרת (`routes` בכרטיס הסוכן, מקור אחד) וכוללת את המסכים החדשים (קבצים, מסמכים, מעבר מערכת, הגדרות, הצעות מחיר, שירותים, חשבוניות, קבלות, שעון נוכחות). בורר הסניפים בשיחה הוא צ'יפ עם חץ שהרשימה שלו נשארת צמודה אליו בגלילה ובשינוי גודל, ובטלפון נפתח ככרטיס קטן מעל עמוד מעומעם במקום גיליון שמכסה את השיחה.
- סבב 6, פרוסה U6 (סקירת עיצוב, דוח בלבד): צולמו כל המסכים באתר השיווק, ב-CRM, בקונסולה ובאפליקציה (גרסת הדפדפן), 725 צילומים בעברית ובאנגלית, בהיר וכהה, מחשב ונייד, ודורגו לפי מדד העיצוב. 35 ממצאים (9 בולטים, 13 בינוניים, 13 קטנים); סיכום ב-`docs/reviews/archive/design-audit-2026-10.md`, הדוח המלא עם צילומים בתיקיית הפרויקט `design-audit-2026-10/`. התיקונים הם פרוסה U7.
- סבב 6, פרוסה T2 (תבניות מסמכים): עסק יכול להוציא חשבונית מס / קבלה, חשבונית מס, חשבונית זיכוי, הצעת מחיר וחשבון עסקה, לכל סוג תבנית משלו בתוך מסגרת המותג (מסגרת אפורה ו"לתשלום עד" בולט לחשבונית, פס אדום עדין לזיכוי, כותרת גדולה ואזור חתימה להצעה, "זו אינה חשבונית מס" לחשבון עסקה). לכל סוג מספור רץ משלו לכל עסק, בלי חורים, שמתחיל ב-1001. ה-PDF שהופק נשמר עם hash ולא משתנה (טעות מתקנים בחשבונית זיכוי); הורדה נוספת יכולה להיות העתק מסומן. עוסק פטור מקבל הצעת מחיר וחשבון עסקה בלי מע"מ ואין לו מסמכי מס; מסמך מס דורש גם מספר עסק וכתובת (מוכנות משפטית מ-K2). חשבונית מס מעל סף ההקצאה (5,000 ש"ח לפני מע"מ, קבוע אחד בקוד) מציינת שמספר ההקצאה ממתין, עד שספק החשבוניות (#47, עדיין מתאם כבוי) יספק אותו; כל מסמך מסומן כדוגמה עד אז. מיגרציה 0105. פרוסה T3 מוסיפה את המסכים: ב-CRM תחת כסף > חשבוניות רואים את המסמכים שהופקו (סינון לפי סוג והמספר הבא בכל סוג), מפיקים מסמך חדש (סוג, לקוח או שם, שורות, אמצעי תשלום, תאריך לתשלום או תוקף, הערות), פותחים מסמך ומורידים את המקור השמור או העתק מסומן, ומתחילים חשבונית זיכוי מחשבונית עם השורות ממולאות. הטופס מסביר סירובים (עוסק פטור, חסר מספר עסק או כתובת, זיכוי מעל החשבונית). בלי מיגרציה. תלוש שכר נשאר פשוט.
- סבב 6, פרוסה T1 (מנוע PDF): קבלות וחשבוניות MyBiz יורדות כקובץ PDF אמיתי שנוצר בשרת (WeasyPrint, גופני Assistant ו-Plus Jakarta Sans מובנים, עברית מימין לשמאל ואנגלית משמאל לימין, לוגו וצבע המותג של העסק, שורת "הופק באמצעות MyBiz" בתחתית). בדפי הווב יש כפתור "הורדת PDF" ליד "הדפסה"; לקוחות יכולים להוריד מה-API את הקבלה שלהם. פרטי החברה של MyBiz (פרטים פיקטיביים) נמצאים ב-`packages/i18n/brand.json` תחת `legal`, ובסביבת הבדיקה יש סימן מים של מסמך לדוגמה. ספקי הקבלות והחשבוניות (#46, #47) נשארים מתאמים כבויים.
- סבב 6, פרוסה M1 (מרכז מעבר, ליבה): עמוד חדש "עוברים ל-MyBiz" (`/migration`, ההרשאה `migration.manage` לבעלים ולמנהלים) להעברת עסק קיים ממערכת אחרת. בעל העסק מאשר שיש לו זכות להעביר את המידע, מעלה קבצי CSV או Excel (נשמרים בתיקיית הייבוא ל-30 יום), מציין מה יש בכל קובץ (לקוחות, מנויים וכרטיסיות עם יתרה ותוקף, שירותים, צוות, תורים עתידיים) ואיזו עמודה היא איזה שדה, ורואה ריצה יבשה של מה בדיוק ייווצר (כפילויות, בעיות ושורות שהושארו בחוץ מפורטות). הייבוא רץ בסדר הנכון ורושם כל מה שיצר במנה אחת; אפשר לבטל מנה במשך 14 יום, והביטול מסיר רק מה שאף אחד לא נגע בו (רשומה שנערכה נשארת אלא אם ביקשו אחרת, ורשומה שמידע מאוחר יותר תלוי בה נשארת תמיד). אנשי צוות הופכים להזמנות (קישורים שמוצגים פעם אחת), לא למשתמשים. מיגרציה 0110. מיפוי AI, תבניות שמורות למערכות מוכרות, הודעה ללקוחות ושירות "תעשו בשבילי" הן פרוסות M2 ו-M3.
- סבב 6, פרוסה M2 (מיפוי AI למרכז המעבר, בלי מיגרציה): בקובץ מעבר יש כפתור "מיפוי העמודות בעזרת AI" שממלא את העמודות ששמות הכותרות לא הסבירו, ואת סוג הקובץ כשהוא לא ידוע. ה-AI רואה רק כותרות ודוגמה אחת לכל עמודה (מספרי ת.ז., כרטיס וטלפון מוסתרים, מיילים מוחלפים) ועונה ב-JSON שהשרת מאמת מול השדות האמיתיים (עמודה לא בטוחה, מתחת ל-50%, נשארת לא ממופה; עמודות שזוהו לא משתנות). זה רץ בתוך מכסת ה-AI וההגבלות הקיימות (אירוע שימוש `ai_credits`, עד 20 בכל מעבר). תבניות שמורות (ייצוא אנשי קשר של Google ושל Outlook) נקראות לפני כל ניחוש. אפשר להעלות גם קובצי אנשי קשר `.vcf` וקובצי יומן `.ics`; ליד כל עמודה רואים כמה ה-AI היה בטוח; ובשלב ההתחלה יש מדריך ייצוא לכל מקור. אירוע ביומן מקבל לקוח רק אם יש בו שם משתתף; השאר מופיעים כשגיאות בריצה היבשה לתיקון או דילוג.
- סבב 6, פרוסה M3 (הודעה ללקוחות ומעבר "תעשו בשבילי", בלי מיגרציה): אחרי ייבוא, בעמוד "עוברים ל-MyBiz" יש שלב "מספרים ללקוחות". כותבים את ההודעה (טקסט מוכן עם שם הלקוח, העסק, קוד ההצטרפות וקישור האפליקציה, עם תצוגה מקדימה כפי שהלקוח הראשון יקבל) והיא נשלחת ללקוחות שהמעבר יצר באימייל, בהתראה לנייד ובחלון באפליקציה, פעם אחת לכל מעבר. וואטסאפ ו-SMS עדיין לא נשלחים מ-MyBiz: ללקוחות עם מספר טלפון בלבד יש כפתור שפותח וואטסאפ עם ההודעה מוכנה, לשליחה מהטלפון שלכם. רשימת "שבוע מקביל" עוזרת לסגור את המערכת הישנה, והכפתור "לבקש מצוות MyBiz לעשות את זה" (זמין גם בזמן ההכנה) פותח משימה בתיבת הפניות של הקונסולה ומאפשר לתמיכה של MyBiz להציץ בעסק למשך השעות שהבעלים בוחר; הבעלים עדיין מאשר את הריצה היבשה.
- סבב 6, פרוסה F1 (קבצי העסק): אזור קבצים חדש (`/files` ב-CRM, "המסמכים שלי" באפליקציית הצוות) עם התיקיות שיש לכל עסק (תלושי שכר, עובדים, מסמכי העסק, ייבוא, כללי) ותיקיות משלו. לכל תיקייה יש הרשאה שפותחת אותה, תלושים ומסמכי עובדים מוצפנים במפתח המערכת לפני השמירה, מסמכים חשבונאיים אפשר רק להעביר לארכיון (נשמרים 7 שנים), תיקיית הייבוא מוחקת קבצים אחרי 30 יום, אפשר להוריד תיקייה כ-ZIP, והקבצים נספרים במכסת האחסון של החבילה. עובד תמיד רואה את הקבצים שתויקו עבורו. הרשאות חדשות `files.read` ו-`files.manage` (בעלים ומנהלים). מיגרציה 0104.
- סבב 6, פרוסה U4 (משתנים בהודעות): בעורך ההודעות יש כפתור "הוספת משתנה" עם רשימה מקובצת (לקוח, מנוי, תורים, עסק וסניף): שם פרטי, משפחה ומלא, טלפון, אימייל, תאריך לידה, 4 ספרות אחרונות של ת.ז., שם המנוי ותאריך סיומו, אימונים שנותרו, התור הבא (זמן, שירות, מדריך), סניף וכתובתו, קישור לאפליקציה, קישור להזמנה וקוד הצטרפות. אפשר לקבוע ערך חלופי למי שאין לו ערך (`{plan_name|חבר}`), התצוגה המקדימה מציגה לקוח לדוגמה, ולפני שליחה העורך מזהיר לכמה נמענים חסר ערך. פונקציית שרת אחת (`render_placeholders`) ממלאת את הנוסח בוואטסאפ, SMS, אימייל, פוש והודעה קופצת. ת.ז. מלאה אף פעם אינה משתנה, רק 4 ספרות אחרונות. טלפון הסניף ויתרת חוב עוד לא מוצעים (אין להם נתונים). בלי מיגרציה.
- סבב 6, פרוסה U1 (דף צוות ה-AI): כשיש שיחה פתוחה אפשר להגדיל את המפה לרוחב מלא (כפתור על המפה או המקש M, נשמר בדפדפן), והשיחה נשארת ככרטיס צף קטן שמחזיר את התצוגה המפוצלת. בורר הסניפים באשף סוכן חדש, בעורך הסוכן ובשיחה נפתח עכשיו מעל הכל ולא נחתך בתוך החלון.
- שלד יומן הלקוח (סבב 4, פרוסה B4): ביומן יש פס ימים עם היום הנבחר במרכז (החלקה או לחיצה, כל יום אחורה וקדימה, קיצור "היום", נקודה בימים עם שיעורים), ומתג יום / שבוע / חודש. בחודש יש רשת ולחיצה על יום יורדת ליום. רכיב משותף ב-`packages/app-kit` (`calendar-strip`).
- מגרשים ותורים ביומן (סבב 4, פרוסה B8): בעסקים שמציגים מגרשים, תצוגת היום והשבוע היא טבלת מגרשים × שעות פנויות (לחיצה על תא מזמינה את המגרש והשעה), ובעסקי תורים כל איש צוות עם השעות הפנויות שלו. המצב נקבע מקטלוג התחומים (`schedule_view`), בלי ענפים לפי תחום. היום והשעה עוברים למסכי ההזמנה.
- סוגי סניף ומדיניות רשת (סבב 4, פרוסה B1): סניף יכול להיות תת-קטגוריה של קטגוריית העסק (למשל סניף פילאטיס וסניף קרוספיט ברשת כושר אחת), הקטלוג קובע לכל קטגוריה איך נראה היומן (`schedule_view`) והאם יש חברים ורשימות משתתפים (`social`), ועסק יכול לנהל לקוחות לכל הרשת או לכל סניף בנפרד (`network_scope`, רשימת "הסניפים שלי" ללקוח). API בלבד; מיגרציה 0081.
- הגדרות סניפים לבעלים (סבב 4, פרוסה B3): ב-CRM הבעלים בוחר סוג סניף בהוספה ובעריכה (רק מתוך קטגוריית העסק) ומחליף את מדיניות לקוחות וחברים (כל הרשת או כל סניף בנפרד) בעמוד הסניפים, עם אישור כשיש יותר מסניף אחד. אזור הבעלים באפליקציה יגיע בפרוסה נפרדת.
- חברים (סבב 4, פרוסה B2): בתוך עסק לקוח יכול לשלוח בקשת חברות לפי קוד אישי, טלפון מדויק או אימייל מדויק, לאשר או לדחות, ולהסיר חבר. חברים רואים שם מלא וסטטיסטיקה משותפת לפי סוג שיעור; משתתפים אחרים בשיעור (בקטגוריות עם רשימות משתתפים) רואים שם פרטי, תמונה, סטטוס ומספר שיעורים משותפים בלבד, ולקוח יכול להסתיר את עצמו מהרשימות. אפשר להזמין חבר לשיעור שנרשמתי אליו: המקום שמור שעתיים (ולא אחרי מועד הביטול), נספר בקיבולת, והחבר מקבל התראה ו-Push. בקטגוריות בלי חברים (קליניקות, יופי, שירותי בית, ושיעורי ילדים כברירת מחדל) אין כל זה. API בלבד; מיגרציה 0082. מסכי האפליקציה יגיעו בפרוסה B7.
- חברים באפליקציה (סבב 4, פרוסה B7): בפרופיל הלקוח שורת "חברים" (רק בעסק שמציע חברים) פותחת מסך עם קוד החבר שלי (שיתוף), הוספה לפי קוד/טלפון/אימייל, בקשות, החברים שלי, הזמנות לשיעורים (אישור/דחייה/ביטול) ומתג "הצג אותי ברשימות משתתפים". מסך אדם מציג תמונה, שם, סטטוס ושיעורים משותפים (לפי סוג שיעור לחברים) עם הוספה והסרה של חבר; בכרטיס שיעור שנרשמתי אליו רואים מי מגיע ואפשר להזמין חבר. קריאת API חדשה לבקשת חברות ממשתתף בשיעור. ההזמנה בתוך בלוק השיעור תתחבר ליומן החדש (B5).
- מחליף סניף ומחליף עסק ביומן הלקוח (סבב 4, פרוסה B6): בראש היומן מחליף סניפים (צ'יפים עד ארבעה סניפים, תפריט מעבר לכך) עם סינון מהיר לפי סוג סניף (למשל כוח, פילאטיס), וצ'יפים של עסקים ללקוח בכמה עסקים. החלפת עסק טוענת מחדש מיתוג, יומן, חברים ומנויים ומאפסת את סינון הסניף; בפרופיל הבורר נקרא "העסק שבו אני לקוח". API: סוג סניף ב-`/client/locations` ו-`location_id` ב-`/client/sessions` (בלי מיגרציה).
- נתוני דמו לכל סוג יומן (סבב 4, פרוסה B9): דמו חדש `categories` יוצר לבעלים אחד את Iron & Flow (רשת כושר עם סניף כוח וסניף פילאטיס), Padel Nation (שלושה סניפי פאדל, טבלת מגרשים) ואת Glow Beauty (מספרה, תורים). לכל סניף יש עכשיו סוג. מריצים מ-workflow ה-seed-staging (`categories`) או `python -m app.seed --demo categories`.

- **טוקני העיצוב Calm (CRM פרימיום, פרוסה W2-2, PR #549, בלי מיגרציה).** אפליקציית העסק והקונסול נראות עכשיו כמו עיצוב ה-Calm שאושר ב-Figma: רקע אפור-לבן ניטרלי ומצב לילה פחם (לא נייבי), צבע פעולה אחד שטוח, גוונים רכים לסטטוסים, Assistant בגדלים 13 / 15 / 17 / 20 / 24 / 30 עם משקל רגיל וחצי-מודגש בלבד, פינות 10 / 12 / 16, כרטיסים שטוחים עם קו דק וצל רק למה שצף. תפריט הצד והפס העליון בהירים כברירת מחדל (העמודה הכהה נשארת כבחירה); ההדרגות יצאו מהכפתורים, מרצועת הכותרת, מרקע הדף ומפס ההתקדמות. נעשה בטוקנים ב-`globals.css` (הבלוק `.app-shell` ממפה מחדש את הגדלים, המשקלים והפינות של Tailwind), כך שכל המסכים עוברים יחד; רכיבי Calm לכל מסך יגיעו ב-W3. אתר השיווק שומר על הצורות שלו. לפני/אחרי: `docs/reviews/current/calm-w2-2`.
- **פתיח חדש לדף הבית (CRM פרימיום, פרוסה W2-6, אתר הנחיתה בלבד).** המסך הראשון הוא עכשיו "העסק שלך עובד. גם כשאתם ישנים.": שעון של 24 שעות רץ מחצות עד השעה האמיתית אצל המבקר, ובדרך קורים דברים בעסק (ליד שסוכן ה-AI ענה בלילה, תזכורות בזריחה, תשלום בצהריים) ושלושה מונים (תורים, הודעות שנענו, הכנסות) עולים יחד איתו. אפשר לגרור אותו בעכבר, להקיש עליו בטלפון או להזיז בחיצים (קורא מסך שומע אותו כמחוון), ולהריץ את כל היממה מחדש. הוא מתאים לבהיר ולכהה, בטלפון השעון יושב בין הכותרת לטקסט, ולמי שביקש הפחתת תנועה הוא מופיע מוכן בלי ריצה. בלי ספרייה חדשה: SVG ו-CSS ורכיב קטן (`day-clock.tsx`); סצנת האריחים המעופפים הישנה נמחקה.
- **חלון אחד, חלון אישור אחד, הדרכה אחת (CRM פרימיום, פרוסה W1-2, בלי מיגרציה).** כל חלון נפתח במרכז עם מרווח מהקצוות (בטלפון עולה מלמטה), הדף שמאחוריו כבר לא גולל, וחלון יכול לקבוע על איזה כפתור לעמוד. כל מחיקה או הסרה באתר נשאלת עכשיו בחלון של המוצר (`ConfirmDialog`) במקום הקופסה האפורה של הדפדפן: "ביטול" במוקד, וכפתור הפעולה אדום במחיקות. ההדרכה היא כרטיס אחד שגולש בצורה חלקה בין "באמצע המסך" ל"ליד חלק בדף", בלי הבהוב. דילוג עליה (הכפתור, ה-X או Esc) רק סוגר אותה: הדף נשאר בדיוק איפה שהיה, וסימון "נצפה" נשמר בבקשה פשוטה שלא יכולה להפנות לדף אחר (גם בכרטיס "אתר" בדשבורד). הודעות המערכת של MyBiz משתמשות באותו חלון ומחכות כל עוד הדרכה פתוחה. נבדק בדפדפן ברוחבים 390, 768, 1024 ו-1280 מול מערכת מקומית; בדיקות ה-e2e של צוות ה-AI ושל תפקידים מותאמים עוברות.
- **מפת צוות ה-AI נשארת עגולה (CRM פרימיום, פרוסה W1-3, בלי מיגרציה).** המפה מציגה תמיד את אדיר המנהל באמצע והסוכנים סביבו; קודם, יצירת צוות הפכה אותה לתרשים ארגוני עם קופסאות. עכשיו צוות הוא הילה רכה מאחורי חבריו עם שמו כתווית קטנה על הקשת (חברי הצוות יושבים זה לצד זה על העיגול). התרשים הארגוני הוא תצוגה נפרדת בבורר מפה / מבנה / רשימה, ועריכת המבנה עדיין משתמשת בו.
- **הגדרות חיוב והזמנות בסדר קריאה (בדיקת סדר ב-CRM, משימה S2, בלי מיגרציה).** החיוב נפתח כך: סיכום מנוי פעיל, התוכנית שלך (פתוחה), אמצעי תשלום, שימוש, חשבוניות, פרטי חשבונית, וביטול המנוי בסוף. קודם "שימוש" היה פתוח באמצע והתוכנית סגורה. בהגדרות ההזמנות החריגים לפי שירות ומסלול מקופלים בתוך פרק הביטולים, והחריג לרשימת המתנה בתוך רשימות המתנה, כך שרק הפרק הראשון פתוח. תוויות הביטול הן משפטים מלאים במקום "... לפני", ובדף המנויים הכותרת זהה לתפריט ("מנויים והקפאות"). מי שקיפל או פתח את הפרקים האלה קודם יראה פעם אחת את ברירות המחדל החדשות.
- **עמודי הצוות מסודרים (ביקורת סדר ב-CRM, משימה S8, בלי מיגרציה).** בכל עמוד באזור הצוות יש עכשיו פס לשוניות אחד (עובדים, משמרות, חופשות, שעון נוכחות, החלפות, שכר, בונוסים, מבנה, תפקידים; לשונית מופיעה רק למי שמותר לפתוח אותה) במקום שמונה כפתורים וקישור חזרה, ולכל העמודים רוחב ומרווחים זהים. לחיצה על שורת עובד פותחת את הכרטיס שלו, ושאר הפעולות (תפקיד, סניפים, הרשאות, תעודת זהות, הסרה) בתפריט "..." שקט; "הזמנת עובד" הוא כפתור בכותרת שפותח חלון, והזמנות ממתינות מיד מתחת לרשימה. בכרטיס עובד הפרקים בעמודה אחת, רק הראשון פתוח, וקיפול פרק כבר לא מקפל אותו לכל העובדים (הבחירה נשמרת לכל עובד בנפרד). ארבע הגדרות המשמרות מקובצות תחת כותרת אחת "הגדרות משמרות" מתחת ללוח.
- **דשבורד: החשוב קודם (סריקת הסדר ב-CRM, פרוסה S4, בלי מיגרציה).** הברכה עכשיו ראשונה, אחריה ערימת התראות אחת (חיוב, שימוש, הצעת אתר), אחריה השיעורים של היום ומה שדורש תשומת לב, ואחריהם המספרים. "צעדים ראשונים" הוא שורת התקדמות מקופלת (פתוחה מיד אחרי ההרשמה ונעלמת כשהכל הושלם), לגרפים יש כותרת "מגמות", ורשימת השיעורים הארוכה של היום גוללת בתוך הכרטיס במקום למתוח את הדף.
- **הגדרות בעמודה אחת (ביקורת סדר ה-CRM, פרוסה S1, בלי מיגרציה).** כל נושאי ההגדרות ודף החשבון האישי מציגים עכשיו את הפרקים בעמודה אחת, לפי סדר הקריאה. קודם, במסך רחב, שתי עמודות הציבו פרק פתוח ליד פרק סגור והשאירו חורים ריקים, ולכן הרגשת שהכול קופץ. רק כרטיסי האינטגרציות (קטנים, באותו גובה, לא מתקפלים) נשארים בשתי עמודות במסך רחב, דרך המחלקה החדשה `form-grid`.
- **פרטים קטנים בכל ה-CRM (ביקורת סדר ב-CRM, פרוסה S12, בלי מיגרציה).** מרחק דביק אחד (`--sticky-top`) קובע עכשיו את תפריט הפרקים, את פס הסינון בתוכן ואת כל יעדי הקפיצה, ובטלפון מרווח הקפיצה כולל את פס התפריט, כך שכותרת פרק כבר לא נחתכת מתחתיו. פס השמירה של טופס ארוך (שירות, מסלול, הצעה, חשבונית, לקוח, ליד) נדבק לתחתית המסך גם בדף מלא, כמו בחלון. הודעות: התבניות לצד הכתיבה, ההיסטוריה ברוחב מלא מתחת, והתצוגה המקדימה הריקה מוסתרת בטלפון. הערת הדמו/סימולציה היא רכיב משותף אחד. בלוח השיעורים נשארים כפתור ראשי וקביעת תור, וימים סגורים, רשימות המתנה, פרסום והעתקת שבוע נכנסים ל"עוד"; שבוע עם יותר משני סניפים נפתח כעמודה אחת מאוחדת במקום עמודות חתוכות.
