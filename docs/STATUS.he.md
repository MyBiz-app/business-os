## מה אני צריך ממך (פעולות, מתי שנוח)

1. ✅ **תבניות המייל ב-Supabase**: מוגדרות (נבדק ב-10.10, זהות ל-`supabase/templates/`).
2. ✅ **כתובות החזרה ב-Supabase**: מוגדרות (Site URL ו-`https://business-os-alpha-drab.vercel.app/**`).
3. ✅ **האפליקציות בטלפון (Expo, בחינם)**: פורסמו (10.10) ופתוחות בדפדפן: `mybiz-client-app.vercel.app`, `mybiz-business-app.vercel.app`, `mybiz-staff-app.vercel.app`. אפשר להוסיף למסך הבית. עדכון אחרי שינוי: Actions ← Deploy the Expo apps to the web ← Run workflow.
4. **התחברות עם Google** (כ-10 דקות):
   1. ב-[Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials) יוצרים OAuth client מסוג Web application.
   2. ב-Authorized redirect URIs מדביקים את ה-Callback URL שמופיע ב-[Supabase → Authentication → Sign In / Providers → Google](https://supabase.com/dashboard/project/_/auth/providers). הכתובת נראית כך: `https://<project>.supabase.co/auth/v1/callback`.
   3. מעתיקים את ה-Client ID וה-Client Secret ל-Supabase ומפעילים את Google. הכפתור יופיע באתר לבד, תוך 5 דקות לכל היותר.
4. **התחברות עם Apple** (אופציונלי, אפשר בהמשך). הכפתור כבר באתר, מושבת עם תווית "בקרוב", ויופעל רק אחרי השלבים האלה. צריך חשבון [Apple Developer](https://developer.apple.com/programs/) בתשלום שנתי:
   1. ב-Apple Developer → Identifiers יוצרים App ID (עם Sign in with Apple) ו-Services ID (זה ה-Client ID).
   2. ב-Services ID מגדירים את הדומיין ואת ה-Return URL: ה-Callback של [Supabase → Authentication → Sign In / Providers → Apple](https://supabase.com/dashboard/project/_/auth/providers).
   3. יוצרים Key עם Sign in with Apple ומורידים את קובץ ה-`.p8` (אפשר להוריד פעם אחת בלבד).
   4. ב-Supabase מדביקים את ה-Services ID וה-Secret Key (JWT שנוצר מה-`.p8`, [המדריך של Supabase](https://supabase.com/docs/guides/auth/social-login/auth-apple); הוא פג כל 6 חודשים, צריך לחדש) ומפעילים את Apple.
   5. ב-Vercel מגדירים משתנה סביבה `AUTH_APPLE_ENABLED=true` ועושים deploy. הכפתור יהפוך לפעיל. את ה-`.p8` לא שולחים לי.
5. **להחליף את הסיסמאות הזמניות** של חשבונות הדמו. **לא לשלוח לי** את הסיסמה החדשה.
6. **החלטות פתוחות:** [#46](https://github.com/MyBiz-app/business-os/issues/46) ספק סליקה (ממנו יגיעו גם Apple Pay ו-Google Pay), [#47](https://github.com/MyBiz-app/business-os/issues/47) ספק חשבוניות, [#36](https://github.com/MyBiz-app/business-os/issues/36) שם המותג. הספקים יחוברו כשהעסק יתחיל לפעול (X21), והשם הוא MyBiz בינתיים.
7. **דוח התיקונים והשיפורים** שלך, לפני העלייה לאוויר.
8. **להדליק אחסון קבצים (2 דקות, מתי שנוח לפני העלייה לאוויר).** ב-[Supabase → Project Settings → API Keys](https://supabase.com/dashboard/project/mywfwzdrlbpxeheszasd/settings/api-keys) מעתיקים את ה-secret key, וב-Render (שירות ה-API ← Environment) מוסיפים `API_STORAGE_PROVIDER` = `supabase` ו-`API_STORAGE_SETTINGS` = `{"url": "https://mywfwzdrlbpxeheszasd.supabase.co", "service_key": "<המפתח הסודי>"}`. **לא לשלוח לי** את המפתח.
9. **להדליק ניטור שגיאות (10 דקות, לפני העלייה לאוויר).** פותחים חשבון [Sentry](https://sentry.io) חינמי ושלושה פרויקטים (Python, Next.js, React Native) ומגדירים את שלושת ה-DSN לפי `docs/monitoring.md`. אפשר להוסיף גם ניטור זמינות חיצוני חינמי על `/health/ready`.
10. **משימות AI מתוזמנות, בדיקה כל 10 דקות (2 דקות, כשנוח).** ב-GitHub: Settings ← Secrets and variables ← Actions ← New repository secret, בשם `API_INTERNAL_TOKEN`, והדביקו את אותו ערך שמוגדר כ-`API_INTERNAL_TOKEN` ב-Render. עד אז משימות רצות רק בלחיצה על "הרצה עכשיו".

12. **הדיפלוי היחיד ל-Vercel (כשהכול גמור).** מיזוג ל-main כבר לא מפרסם כלום (ב-Vercel Hobby יש מגבלה של 100 דיפלויים ביום). כשהעבודה גמורה: GitHub ← Actions ← להריץ **"Deploy web to Vercel"** (האתר וה-CRM, `business-os-alpha-drab.vercel.app`), ואחריו **"Deploy the Expo app to the web (Vercel)"** עם app = `all` (`mybiz-client-app.vercel.app`). שניהם ידניים בלבד. קודם להריץ מיגרציות עם "Migrate staging database". (העדכון של EAS אינו דיפלוי ל-Vercel ולא השתנה.)

## בעבודה

- סבב 6, פרוסה T2 (תבניות מסמכים): עסק יכול להוציא חשבונית מס / קבלה, חשבונית מס, חשבונית זיכוי, הצעת מחיר וחשבון עסקה, לכל סוג תבנית משלו בתוך מסגרת המותג (מסגרת אפורה ו"לתשלום עד" בולט לחשבונית, פס אדום עדין לזיכוי, כותרת גדולה ואזור חתימה להצעה, "זו אינה חשבונית מס" לחשבון עסקה). לכל סוג מספור רץ משלו לכל עסק, בלי חורים, שמתחיל ב-1001. ה-PDF שהופק נשמר עם hash ולא משתנה (טעות מתקנים בחשבונית זיכוי); הורדה נוספת יכולה להיות העתק מסומן. עוסק פטור מקבל הצעת מחיר וחשבון עסקה בלי מע"מ ואין לו מסמכי מס; מסמך מס דורש גם מספר עסק וכתובת (מוכנות משפטית מ-K2). חשבונית מס מעל סף ההקצאה (5,000 ש"ח לפני מע"מ, קבוע אחד בקוד) מציינת שמספר ההקצאה ממתין, עד שספק החשבוניות (#47, עדיין מתאם כבוי) יספק אותו; כל מסמך מסומן כדוגמה עד אז. מיגרציה 0105. פרוסה T3 מוסיפה את המסכים: ב-CRM תחת כסף > חשבוניות רואים את המסמכים שהופקו (סינון לפי סוג והמספר הבא בכל סוג), מפיקים מסמך חדש (סוג, לקוח או שם, שורות, אמצעי תשלום, תאריך לתשלום או תוקף, הערות), פותחים מסמך ומורידים את המקור השמור או העתק מסומן, ומתחילים חשבונית זיכוי מחשבונית עם השורות ממולאות. הטופס מסביר סירובים (עוסק פטור, חסר מספר עסק או כתובת, זיכוי מעל החשבונית). בלי מיגרציה. תלוש שכר נשאר פשוט.
- סבב 6, פרוסה T1 (מנוע PDF): קבלות וחשבוניות MyBiz יורדות כקובץ PDF אמיתי שנוצר בשרת (WeasyPrint, גופני Assistant ו-Plus Jakarta Sans מובנים, עברית מימין לשמאל ואנגלית משמאל לימין, לוגו וצבע המותג של העסק, שורת "הופק באמצעות MyBiz" בתחתית). בדפי הווב יש כפתור "הורדת PDF" ליד "הדפסה"; לקוחות יכולים להוריד מה-API את הקבלה שלהם. פרטי החברה של MyBiz (פרטים פיקטיביים) נמצאים ב-`packages/i18n/brand.json` תחת `legal`, ובסביבת הבדיקה יש סימן מים של מסמך לדוגמה. ספקי הקבלות והחשבוניות (#46, #47) נשארים מתאמים כבויים.
- סבב 6, פרוסה M1 (מרכז מעבר, ליבה): עמוד חדש "עוברים ל-MyBiz" (`/migration`, ההרשאה `migration.manage` לבעלים ולמנהלים) להעברת עסק קיים ממערכת אחרת. בעל העסק מאשר שיש לו זכות להעביר את המידע, מעלה קבצי CSV או Excel (נשמרים בתיקיית הייבוא ל-30 יום), מציין מה יש בכל קובץ (לקוחות, מנויים וכרטיסיות עם יתרה ותוקף, שירותים, צוות, תורים עתידיים) ואיזו עמודה היא איזה שדה, ורואה ריצה יבשה של מה בדיוק ייווצר (כפילויות, בעיות ושורות שהושארו בחוץ מפורטות). הייבוא רץ בסדר הנכון ורושם כל מה שיצר במנה אחת; אפשר לבטל מנה במשך 14 יום, והביטול מסיר רק מה שאף אחד לא נגע בו (רשומה שנערכה נשארת אלא אם ביקשו אחרת, ורשומה שמידע מאוחר יותר תלוי בה נשארת תמיד). אנשי צוות הופכים להזמנות (קישורים שמוצגים פעם אחת), לא למשתמשים. מיגרציה 0110. מיפוי AI, תבניות שמורות למערכות מוכרות, הודעה ללקוחות ושירות "תעשו בשבילי" הן פרוסות M2 ו-M3.
- סבב 6, פרוסה F1 (קבצי העסק): אזור קבצים חדש (`/files` ב-CRM, "המסמכים שלי" באפליקציית הצוות) עם התיקיות שיש לכל עסק (תלושי שכר, עובדים, מסמכי העסק, ייבוא, כללי) ותיקיות משלו. לכל תיקייה יש הרשאה שפותחת אותה, תלושים ומסמכי עובדים מוצפנים במפתח המערכת לפני השמירה, מסמכים חשבונאיים אפשר רק להעביר לארכיון (נשמרים 7 שנים), תיקיית הייבוא מוחקת קבצים אחרי 30 יום, אפשר להוריד תיקייה כ-ZIP, והקבצים נספרים במכסת האחסון של החבילה. עובד תמיד רואה את הקבצים שתויקו עבורו. הרשאות חדשות `files.read` ו-`files.manage` (בעלים ומנהלים). מיגרציה 0104.
- סבב 6, פרוסה U4 (משתנים בהודעות): בעורך ההודעות יש כפתור "הוספת משתנה" עם רשימה מקובצת (לקוח, מנוי, תורים, עסק וסניף): שם פרטי, משפחה ומלא, טלפון, אימייל, תאריך לידה, 4 ספרות אחרונות של ת.ז., שם המנוי ותאריך סיומו, אימונים שנותרו, התור הבא (זמן, שירות, מדריך), סניף וכתובתו, קישור לאפליקציה, קישור להזמנה וקוד הצטרפות. אפשר לקבוע ערך חלופי למי שאין לו ערך (`{plan_name|חבר}`), התצוגה המקדימה מציגה לקוח לדוגמה, ולפני שליחה העורך מזהיר לכמה נמענים חסר ערך. פונקציית שרת אחת (`render_placeholders`) ממלאת את הנוסח בוואטסאפ, SMS, אימייל, פוש והודעה קופצת. ת.ז. מלאה אף פעם אינה משתנה, רק 4 ספרות אחרונות. טלפון הסניף ויתרת חוב עוד לא מוצעים (אין להם נתונים). בלי מיגרציה.

- שלד יומן הלקוח (סבב 4, פרוסה B4): ביומן יש פס ימים עם היום הנבחר במרכז (החלקה או לחיצה, כל יום אחורה וקדימה, קיצור "היום", נקודה בימים עם שיעורים), ומתג יום / שבוע / חודש. בחודש יש רשת ולחיצה על יום יורדת ליום. רכיב משותף ב-`packages/app-kit` (`calendar-strip`).

- סוגי סניף ומדיניות רשת (סבב 4, פרוסה B1): סניף יכול להיות תת-קטגוריה של קטגוריית העסק (למשל סניף פילאטיס וסניף קרוספיט ברשת כושר אחת), הקטלוג קובע לכל קטגוריה איך נראה היומן (`schedule_view`) והאם יש חברים ורשימות משתתפים (`social`), ועסק יכול לנהל לקוחות לכל הרשת או לכל סניף בנפרד (`network_scope`, רשימת "הסניפים שלי" ללקוח). API בלבד; מיגרציה 0081.
- הגדרות סניפים לבעלים (סבב 4, פרוסה B3): ב-CRM הבעלים בוחר סוג סניף בהוספה ובעריכה (רק מתוך קטגוריית העסק) ומחליף את מדיניות לקוחות וחברים (כל הרשת או כל סניף בנפרד) בעמוד הסניפים, עם אישור כשיש יותר מסניף אחד. אזור הבעלים באפליקציה יגיע בפרוסה נפרדת.
- חברים (סבב 4, פרוסה B2): בתוך עסק לקוח יכול לשלוח בקשת חברות לפי קוד אישי, טלפון מדויק או אימייל מדויק, לאשר או לדחות, ולהסיר חבר. חברים רואים שם מלא וסטטיסטיקה משותפת לפי סוג שיעור; משתתפים אחרים בשיעור (בקטגוריות עם רשימות משתתפים) רואים שם פרטי, תמונה, סטטוס ומספר שיעורים משותפים בלבד, ולקוח יכול להסתיר את עצמו מהרשימות. אפשר להזמין חבר לשיעור שנרשמתי אליו: המקום שמור שעתיים (ולא אחרי מועד הביטול), נספר בקיבולת, והחבר מקבל התראה ו-Push. בקטגוריות בלי חברים (קליניקות, יופי, שירותי בית, ושיעורי ילדים כברירת מחדל) אין כל זה. API בלבד; מיגרציה 0082. מסכי האפליקציה יגיעו בפרוסה B7.
- חברים באפליקציה (סבב 4, פרוסה B7): בפרופיל הלקוח שורת "חברים" (רק בעסק שמציע חברים) פותחת מסך עם קוד החבר שלי (שיתוף), הוספה לפי קוד/טלפון/אימייל, בקשות, החברים שלי, הזמנות לשיעורים (אישור/דחייה/ביטול) ומתג "הצג אותי ברשימות משתתפים". מסך אדם מציג תמונה, שם, סטטוס ושיעורים משותפים (לפי סוג שיעור לחברים) עם הוספה והסרה של חבר; בכרטיס שיעור שנרשמתי אליו רואים מי מגיע ואפשר להזמין חבר. קריאת API חדשה לבקשת חברות ממשתתף בשיעור. ההזמנה בתוך בלוק השיעור תתחבר ליומן החדש (B5).
- מחליף סניף ומחליף עסק ביומן הלקוח (סבב 4, פרוסה B6): בראש היומן מחליף סניפים (צ'יפים עד ארבעה סניפים, תפריט מעבר לכך) עם סינון מהיר לפי סוג סניף (למשל כוח, פילאטיס), וצ'יפים של עסקים ללקוח בכמה עסקים. החלפת עסק טוענת מחדש מיתוג, יומן, חברים ומנויים ומאפסת את סינון הסניף; בפרופיל הבורר נקרא "העסק שבו אני לקוח". API: סוג סניף ב-`/client/locations` ו-`location_id` ב-`/client/sessions` (בלי מיגרציה).
- נתוני דמו לכל סוג יומן (סבב 4, פרוסה B9): דמו חדש `categories` יוצר לבעלים אחד את Iron & Flow (רשת כושר עם סניף כוח וסניף פילאטיס), Padel Nation (שלושה סניפי פאדל, טבלת מגרשים) ואת Glow Beauty (מספרה, תורים). לכל סניף יש עכשיו סוג. מריצים מ-workflow ה-seed-staging (`categories`) או `python -m app.seed --demo categories`.

## הושלם (עבודה אחרונה)
- מבנה צוות ה-AI (סבב 6, פרוסה U3): בדף צוות ה-AI יש מצב "עריכת מבנה" למי שמנהל את צוות ה-AI. גוררים את העיגול שמעל סוכן אל הסוכן שהוא מדווח לו, לוחצים על קו כדי למחוק אותו, מזיזים סוכנים ידנית וגוררים סוכן לתוך מסגרת צוות כדי להוסיף אותו. אותה עריכה זמינה גם מרשימות ("מדווח ל", צוות, ראש צוות) לשימוש במקלדת, בקורא מסך ובטלפון. המפה נבנית מחדש כעץ. כללים: המנהל הראשי תמיד למעלה, אין מעגלים, סוכן נעול מוצג אך לא ניתן לחיבור. למבנה יש משמעות: המנהל הראשי מעביר שאלה קודם לראש הצוות, ובהנחיות של כל סוכן כתוב למי הוא מדווח ובאיזה צוות הוא. מיגרציה 0111. עדיין לא: תדריך בוקר מקובץ לפי צוותים.
- הרשמה ומוכנות משפטית (סבב 6, פרוסה K2): אשף ההרשמה שואל עכשיו את סוג העסק (חברה, עוסק מורשה, עוסק פטור, עמותה, שותפות, אחר; חובה בישראל) ומזהיר, בלי לחסום, כשמספר חברה לא מתחיל ב-51. בהגדרות יש כרטיס "מוכנות משפטית" שמראה מה מולא (סוג, מספר עסק, כתובת, תיק ניכויים, רישיון עסק לא חובה עם תוקף) ומה כל פרט חסר יפתח: חשבונית מס צריכה כתובת, שכר צריך תיק ניכויים, עוסק פטור מפיק קבלות בלבד. הרישיון אף פעם לא חובה; 60 יום לפני שהוא פג (או אחרי שפג) מופיעה תזכורת ב"דורש את תשומת לבך" בלוח הבקרה. API `GET /tenants/current/readiness`; מיגרציה 0103.
- סידור חשבון הדמו (נתוני דמו): מצב חדש ב-seed בשם `curated` (ה-workflow "Seed staging demo data", demo = curated, בלי replace) מצמצם את חשבון הדמו של הבעלים לשלושה עסקים: חדר הכושר "Adir fitness" (עסק אחד עם סניפים מסוגים שונים: כוח, פילאטיס וקרוספיט), Studio Bloom ו-Urban Slice. "Iron & Flow" קיים מקבל שם חדש במקום, כל עסק אחר שהחשבון הוא הבעלים היחיד שלו נמחק יחד עם אנשי הדמו שלו, ולוגואים ותמונות מתמלאים. אף פעם לא נוגע בעסקים של בעלים אחרים. חדר הכושר בדמו `categories` נקרא עכשיו "Adir fitness".
- שעון נוכחות (סבב 6, פרוסה P2): עובדים נכנסים ויוצאים מהמשמרת באפליקציה ("שעון נוכחות" תחת "אני"): כפתור אחד, מקושר למשמרת המתוכננת, עם 8 הימים האחרונים. ב-CRM, צוות > שעון נוכחות מציג את החודש לכל עובד: שעות מתוכננות מול בפועל, משמרות חסרות (משמרות שעברו בלי שעות מדווחות), שעות נוספות לפי תעריף (125% / 150% / יום מנוחה 150%) וסטטוס אישור. מנהל עם ההרשאה החדשה `time.approve` (בעלים, מנהלים ומנהלי סניף בסניפים שלהם) מוסיף שעות שנשכחו או מתקן רישום עם סיבה חובה (נשמרת ברישום וביומן הפעולות) ואז מאשר את החודש, שננעל עד שפותחים אותו מחדש. כללי השעות הנוספות (שבוע 42 שעות, יום 8.6 או 8 שעות, שעתיים ראשונות ב-125% והשאר ב-150%, שבת ב-150%) הם נתונים לכל עסק (`time_clock_rules`, הבעלים עורכים אותם באותו עמוד) ולא קוד. מיגרציה 0107 מוסיפה `time_clock_entries`, `time_clock_approvals` ו-`time_clock_rules`. עדיין לא: הגבלת כניסה לשעון למיקום הסניף (לסניפים אין קואורדינטות), וימי עבודה לכל עובד מכרטיס העובד (P1); בינתיים אורך שבוע העבודה הוא הגדרה של העסק. שכר (P4) קורא את השעות האלה.
- מספרי זהות (סבב 6, פרוסה K1): מספר הזהות של עובד או לקוח (תעודת זהות ישראלית עם בדיקת ספרת ביקורת, דרכון או תעודה זרה עם מדינה) נשמר בטבלה נפרדת `person_identities` (מיגרציה 0102), מוצפן במפתח הסודות של המערכת, עם גיבוב מפתחי לכל עסק שמונע אותו מספר פעמיים בין עובדים או בין לקוחות, ו-4 התווים האחרונים לתצוגה. במסכים רואים `•••••1234`; המספר המלא נחשף רק למי שיש לו `identity.read` (בעלים) או לאדם עצמו, וכל הוספה, הסרה וחשיפה נרשמות ביומן הביקורת. ברשימת הצוות ב-CRM יש חלונית "תעודת זהות" לכל עובד, בעמוד הלקוח יש אזור זהות כשהעסק מבקש מלקוחות (הגדרה חדשה `client_id_number`: כבויה כברירת מחדל, לא חובה או חובה), ובאפליקציה יש כרטיס ב"הפרטים שלי" לעובדים וללקוחות. נמחק עם העובד או עם מחיקת הלקוח; לא נשלח ל-AI.
- תיק שכר לעובד (סבב 6, פרוסה P1): לכל חבר צוות פרופיל העסקה (מיגרציה 0106): תנאים גלובליים, שעתיים או גלובלי + שעות נוספות, היקף משרה, ימי עבודה, פנסיה וקרן השתלמות, תאריך הודעה לעובד, וחשבון בנק מוצפן (מוצגות רק 4 ספרות אחרונות; חשיפה דורשת `identity.read` ונרשמת ביומן). טופס 101 מתבקש על ידי מנהל שכר, העובד ממלא וחותם באפליקציה (אני > טופס 101, חתימה בהקלדת שם), נשמר מוצפן לכל שנת מס; השרת מחשב נקודות זיכוי (`app/payroll/credit_points.py`) ומנהל שכר יכול לתקן אותן עם הערה. טופס חתום יורד כ-PDF ממותג. הרשאות חדשות: `payroll.read`, `payroll.manage` (בעלים ומנהלים) ו-`payroll.approve` (בעלים בלבד, לשימוש פרוסת ריצת השכר). ב-CRM: צוות > תיק שכר עם ארבע לשוניות (פרטים אישיים, תנאי העסקה, רכיבי שכר עד P3, מסמכים). חוקי נקודות הזיכוי הם טבלת טיוטה עד בדיקת רואה החשבון.
- רכיבי שכר ובונוסים (סבב 6, פרוסה P3): בלשונית השלישית של תיק השכר יש רכיבים קבועים (נסיעות, ארוחות, טלפון, רכב, תוספת קבועה, הבראה, ניכוי קבוע) עם סימון מס, ביטוח לאומי ובסיס פנסיה. עמוד חדש צוות > בונוסים מוסיף בונוס, מתנה לחג, החזר הוצאה או ניכוי חד-פעמי לעובד, סניף, קבוצת סניפים, תפקיד, מנהלים או כולם (עם תצוגה מקדימה, ואפשר לחלק סכום כולל שווה בשווה). מנהל סניף מציע והבעלים מאשר. נוספה טבלת שיעורים מתוארכת (ערכי דוגמה, לא מאומתים). מיגרציה 0108.
- סרגל סינון בתוכן (סבב 6, פרוסה U5): כרטיס הסינון בדף "תוכן וקריאייטיב" הפך לסרגל אחד דביק. חלון בחירת רשתות (אייקון ושם לכל רשת, "בחר הכל"), חלון תקופה (7, 30, 90 יום, החודש, החודש הקודם, טווח מותאם), מתג השוואה וכפתור איפוס. כל שינוי חל מיד בלי כפתור "החל", המצב נשמר בכתובת כך שאפשר לשתף, הרשתות שנבחרו מופיעות כתגיות להסרה, ובטלפון הסרגל מתקפל מאחורי כפתור "סינון (n)". מספר העוקבים לכל רשת עדיין לא מוצג כי רשימת החשבונות לא מחזירה אותו.
- תמונות פרופיל לנתוני הדמו וסניף קרוספיט: מצב חדש ב-seed בשם `profiles` (ה-workflow "Seed staging demo data", demo = profiles, בלי replace) מוסיף, בלי למחוק דבר, לוגו וצבע מותג לכל עסק וסניף בדמו, תמונה לכל איש צוות ול-40 לקוחות בכל עסק, וסניף שלישי (קרוספיט) לרשת Iron & Flow לצד כוח ופילאטיס. התמונות מצוירות (איורים, לא תמונות של אנשים אמיתיים). תמונות הלקוחות מופיעות בפרופיל של הלקוח עצמו; רשימת הלקוחות ב-CRM עדיין לא מציגה אותן.
- נתוני דמו ובדיקת קצה לקצה לסבב 5 (פרוסה D1): כל עסק דמו מגיע עכשיו עם תכונות סבב 5 מלאות: שתי קבוצות סניפים ומנהל סניף אחד (בעסקים עם כמה סניפים), סוכן מובנה שהותאם (סוכן הכספים, רשמי, מוגבל לקבוצה אחת) וסוכן מותאם לקבלה, חודש של שימוש ב-AI לפי סוכן ואדם עם מגבלות קרדיטים לקבלה ולצוות, משימות מתוזמנות לסוכנים (סיכום מכירות שבועי עם שלוש הרצות קודמות, משימה יומית מושהית ומשימה חד-פעמית שהסתיימה), סטודיו התוכן על חשבונות דמו (חמש רשתות ופרופיל Google שני לסניף, ושלוש טיוטות פוסט) וכתובות מענה (דומיין שמור, לא נשלח אליהן כלום). דמו `platform` מוסיף למרכז ההפצה חלון קופץ שנשלח וטיוטת מייל. בדיקה חדשה `e2e/agents.py` (רצה בתהליך End-to-end): עמוד צוות ה-AI, שיחה עם סוכן, לוח המשימות המתוזמנות, סטודיו התוכן, קבוצות סניפים ובחשבון מנהל פלטפורמה גם מרכז ההפצה ולוח ה-AI בקונסולה. כדי לראות ב-staging: מריצים "Seed staging demo data" עם הדמו `networks` (ו-`platform` לקונסולה). הודעות לסניפים (F4) עדיין לא בדמו. בלי מיגרציה.

- AI בקונסולת MyBiz (סבב 5, פרוסה A9): עמוד חדש `/platform/ai` (הרשאת `usage.read`) עם לוח עלויות AI (קרדיטים לכל עסק ב-30 יום עם מגמה, המחיר החודשי של מודולי ה-AI שלו, ורווח לעסקים בדולר, הצורכים הגדולים ראשונים), בחירת מודל לכל רמה, **מתג חירום** שעוצר AI בכל העסקים בבת אחת, והשהיית AI לעסק בודד עם סיבה (שניהם דורשים `billing.manage` ונרשמים ביומן הביקורת של הקונסולה וביומן של העסק). עסק שנעצר מקבל `ai_paused`; העצירה חלה גם על AI בוואטסאפ. צוות ה-AI של MyBiz (מנהל, תמיכה, בריאות עסקים, חיובים, צמיחה) עונה מכלים לקריאה בלבד שדורשים אותה הרשאת קונסולה, מנסח טיוטות בלבד, ורושם כל בדיקה כ-AI הפועל בשם איש הצוות (`ai.tool.*`). - מחברי גוגל וטיקטוק בסטודיו התוכן (סבב 5, פרוסה S3): בעל העסק יכול לחבר מכרטיסי החיבור את יוטיוב (מנויים, צפיות, סרטונים וקהל), גוגל עסקי (ביקורות, דירוג, חיפושים, צפיות בפרופיל, שיחות והוראות הגעה) וטיקטוק (עוקבים, סרטונים והצפיות, הלייקים, התגובות והשיתופים שלהם). ההסכמה מתבצעת בעמוד של הרשת עצמה ומחזירה לעמוד התוכן (`/social/callback/youtube`, `/google_business`, `/tiktok`); הטוקנים מוצפנים, מתחדשים בכל סנכרון, וחשבון שהגישה אליו בוטלה מסומן "צריך להתחבר מחדש". ל-X, לינקדאין, פינטרסט וסנאפצ'ט יש מתאמים כבויים והם נשארים "בקרוב". כל עוד מפתחות המפתחים של גוגל וטיקטוק לא הוגדרו הרשתות האלה נשארות "בקרוב" ושום דבר לא נשבר. פרסום פוסטים עוד לא נבנה. בלי מיגרציה.
- ליבת סטודיו התוכן (סבב 5, פרוסה S1): לשונית "תוכן וקריאייטיב" בתפריט ה-CRM (נעולה עם תצוגה מקדימה והוספה לתוכנית כשהמודול כבוי). בכניסה ראשונה: כרטיס לכל רשת עם מה שהיא נותנת, "בקרוב" ברשתות שעוד אין להן מחבר, וכפתור "הצג עם נתוני דמו". בדשבורד: סינון רשתות (כולן או כל שילוב), תקופה (7/30/90 ימים או מותאם) עם השוואה לתקופה הקודמת, כרטיסי KPI, עוקבים לפי רשת, צפיות שבועיות בסרטונים, מעורבות לפי סוג תוכן, מפת חום של שעות מומלצות, פוסטים מובילים, קהל, נתוני גוגל עסקי, ייצוא CSV והדפסה. מודול חדש `social_studio` (מחיר זמני 39 ₪ / 12 $ / 11 € לחודש, במחירון ובדף `/upgrade/social`), הרשאות `social.read` ו-`social.manage` (בעלים ומנהל), רישום ספקים לרשתות (`app/social/providers.py`), ספק דמו אמין, היסטוריה יומית משלנו ו-job יומי `sync-social`. המחברים האמיתיים (Meta, יוטיוב, טיקטוק, גוגל) הם פרוסות S2 ו-S3; שלב באשף ההרשמה וכלי הסוכנת שירה יבואו אחר כך. מיגרציה 0093.
- מחבר Meta (סבב 5, פרוסה S2): פייסבוק (עמודים), אינסטגרם עסקי (באותה כניסה לפייסבוק) ו-Threads (כניסה משלו) מתחברים באמת מסטודיו התוכן. הבעלים מאשר בדף של Meta, חוזר ל-`/social/callback/{provider}`, בוחר אילו עמודים וחשבונות לחבר (חשבון אחד מתחבר מיד), והדשבורד מתמלא בעוקבים, חשיפה, צפיות, מעורבות, פוסטים מובילים ובאינסטגרם גם קהל. אפשר לפרסם פוסט מה-API (`POST /social/accounts/{id}/publish`, באינסטגרם חובה תמונה). הטוקנים מוצפנים, טוקן שפג תוקפו (Threads) מתחדש לבד, וטוקן שנדחה מסמן את החשבון "צריך לחבר מחדש". דורש `API_META_APP_ID` ו-`API_META_APP_SECRET` (ל-Threads: `API_META_THREADS_APP_ID` ו-`API_META_THREADS_APP_SECRET`); בלעדיהם הרשתות נשארות "בקרוב". גרסת ה-Graph API ב-`API_META_GRAPH_VERSION` (ברירת מחדל v26.0). מיגרציה 0098.
- שירה, סוכנת התוכן (סבב 5, פרוסה S4): שירה קוראת את מספרי הסטודיו (`social_overview`, `top_posts`, `audience_summary`), שומרת טיוטות פוסטים (`draft_post`, `list_drafts`) ומציעה לפרסם טיוטה בחשבון מחובר (`publish_post`); שום דבר לא יוצא עד שהבעלים לוחץ על כרטיס האישור, והחשבון נבדק שוב ברגע האישור. שיחה שמוגבלת לסניפים רואה רק חשבונות של אותם סניפים. באפליקציית העסק יש מסך "תוכן וקריאייטיב" (מהיום): רשתות מחוברות, סינון לפי תקופה ורשת, מספרים עיקריים עם שינוי, מגמת עוקבים, פוסטים מובילים, הטיוטות של שירה (עם מחיקה) וכפתור לשאול אותה. כרטיס האישור מציג את הפוסט באפליקציה ובאתר. מיגרציה 0097 (`social_drafts`).
- גיוס סוכן AI (סבב 5, פרוסה A4): כפתור "גייס סוכן" בדף צוות ה-AI פותח אשף בשישה שלבים (תבנית נושא, שם צבע ופנים מגלריה של 16 פנים או תמונה שהועלתה וחתוכה לעיגול, מה הסוכן עושה / מה אסור לו / מה הוא יודע, לאילו חלקים בעסק ולאילו סניפים יש לו גישה, אילו תפקידים רשאים להשתמש בו, ושיחת ניסיון לפני שמשהו נשמר). סוכן הניסיון הוא טיוטה שרק מנהלים יכולים לדבר איתה, והיא נמחקת אם האשף נסגר. אפשר לערוך כל סוכן (מובנה או מותאם) מכפתור ההגדרות בשיחה איתו: שם, פנים, צבע, הוראות, טון, ארגז כלים, סניפים, תפקידים, איכות מודל, הפעלה וכיבוי, והסרה של סוכן מותאם. החבילה מאפשרת 3 סוכנים מותאמים עם AI Basic ו-10 עם AI Pro. - מנהל סניף (סבב 5, פרוסה G2): תפקיד מערכת חדש `branch_manager` עם הרשאות מנהל בסניפים שלו בלבד (עובדים, משמרות, הזמנות, לקוחות ודוחות של אותם סניפים) ובלי שום דבר ברמת העסק (קטלוג, הגדרות, תקציב AI, תפקידים מותאמים וסניפים חדשים). בדף הסניף בעל העסק או מנהל ממנה עובד למנהל הסניף (`PUT /locations/{id}/manager`); עד אז בעל העסק מנהל אותו (`locations.manager_user_id`, מיגרציה 0086). מנהל סניף מוסיף ועורך עובדים וקבלה רק בתוך הסניפים שלו, לא יכול לתת הרשאה שאין לו או למנות בעלים, מנהלים ומנהלי סניף אחרים, ורואה רק את אנשי הסניפים שלו; הזמנה נושאת את הסניפים שהחבר החדש יהיה משויך אליהם. עובדי הסניף מקבלים את מנהל הסניף כ-`reports_to` מוצע בתרשים הארגוני. מנהל סניף בלי סניף לא מקבל גישה בכלל (אף פעם לא "כל הסניפים"). הכול נאכף בשרת, וצוות ה-AI מכבד את זה דרך אותו היקף סניפים.
- עלויות AI ותמחור (סבב 5, פרוסה A2): קרדיטים נוספים בתשלום לפי שימוש (כבוי כברירת מחדל, תקרה חודשית אופציונלית, מופיע בדף החיוב), מגבלות חודשיות לפי תפקיד ולפי אדם, התראות ב-80/100/150/200% מהקרדיטים הכלולים, ושלושת מודולי הסוכנים (אנליטיקה, כספים ושיווק) נפתחים לבחירה במקום "בקרוב". ה-API: `GET/PUT /ai/spend` ו-`PUT /ai/spend/limits`; מיגרציה 0086. התראות במייל ומסך המגבלות יגיעו בהמשך.

- עיגול ה-AI הצף (סבב 5, פרוסה A5): כפתור עגול בגודל 56px בפינת הסיום של כל מסכי ה-CRM חוץ מדף צוות ה-AI (כפתור הנגישות נשאר בפינה השנייה). הוא מציג את הסוכן שמתאים למסך ועובר בעדינות לסוכן אחר כשעוברים מסך (לידים והודעות: שיווק; יומן ואירועים: מזכירה; מכירות והצעות: מכירות; חשבונות וקבלות: כספים; צוות: צוות; דוחות ולוח בקרה: אנליסט; בכל מקום אחר המנהל הראשי; מפה אחת ב-`lib/ai-bubble.ts`). ריחוף, פוקוס מקלדת, לחיצה ארוכה (או הנגיעה הראשונה במסך מגע) פותחים מניפה של עד חמישה סוכנים, ו-Escape סוגר. לחיצה פותחת חלון שיחה קטן (400px) שמעביר לסוכן את הקשר המסך (בדף לקוח הוא יודע על איזה לקוח מדובר) וקישור לצוות המלא. בלי מיגרציה. עדיין לא: הנקודה האדומה להתראה (דורשת את ההתראות היזומות של A8).
- ה-AI באפליקציית העסק (סבב 5, פרוסה A7): כפתור ניצוצות צף מעל הלשוניות היום, לקוחות, תיבה ומספרים, שפותח את הסוכן שמתאים ללשונית (מזכירה, שיווק, שיווק, אנליסט; המנהל הראשי בשאר המקומות או כשהסוכן נעול) ומעביר לו את הלשונית כהקשר. הכפתור "צוות ה-AI שלך" במסך היום מציג את הסוכנים (פנים, תפקיד, נעולים בעמעום); לחיצה פותחת שיחה במסך מלא עם רצועה להחלפת סוכן, שאלות מוצעות, שיחה חדשה והסניף הנוכחי כהיקף. כרטיסים שהסוכן מכין (קביעה, ביטול, רישום שעות, חיוב חודש) מציגים אישור ו"לא לבצע", והשרת בודק שוב באישור כמו באתר. דורש הרשאת `ai.use` ומודול AI. בלי מיגרציה ובלי API חדש. עדיין לא: תשובות בסטרימינג, היסטוריית שיחות, פנים מוכנות בטלפון (אותיות אם לא הועלתה תמונה), הנקודה האדומה (A8).
- ליבת סוכני ה-AI (סבב 5, פרוסה A1): צוות ה-AI כתשעה סוכנים מובנים (מנהל ראשי, מזכירה, שיווק, מכירות, כספים, צוות, שירות לקוחות, אנליסט, תוכן) ועוד סוכנים מותאמים. בעלים ומנהלים (הרשאה חדשה `ai.manage`) משנים שם, מכבים סוכן, קובעים מי רשאי להשתמש בו, מגבילים אותו לסניפים ובוחרים רמת מודל. כל כלי של העוזר מכבד עכשיו את הסניפים של המשתמש, של הסוכן ושל השיחה (סוכן של הדרום לא רואה מספרים של הצפון), כל סוכן מקבל רק את ארגז הכלים שלו, המנהל הראשי יכול להציע מעבר למומחה, שיחות שייכות לסוכן וניתנות לארכוב, והשימוש נספר לפי סוכן ועובד. API תחת `/ai/*`, מיגרציה 0083. תוקן גם כלי רשימת המשתתפים שקרס. המסכים יגיעו ב-A3.
- משימות מתוזמנות לסוכני AI (סבב 5, פרוסה A10): אומרים לסוכן "מחר ב-9:00 תשלח הודעה ללידים שלא ענו" או "כל יום ראשון ב-8:00 תשלח לי סיכום שבועי", והוא מכין כרטיס (מה, מתי, פעם אחת או חוזר, עד 20 קרדיטים להרצה) שמאשרים. המשימה נכנסת ללוח "משימות מתוזמנות" בדף צוות ה-AI (`/ai`): ההרצה הבאה, השהיה, חידוש, שינוי שעה, הרצה עכשיו, מחיקה והיסטוריה של כל הרצה. שני סוגים: פעולה מתוזמנת (הזמנה, ביטול או חיוב חודשי שאישרתם, ונבדקת שוב בזמן הביצוע כמו אישור רגיל) והרצת סוכן (הוראה שהסוכן מבצע, לקריאה בלבד; כל מה שהוא מציע ממתין עד 3 ימים לאישורכם). משימה רצה בשם מי שיצר אותה ועם ההרשאות שלו היום; אם הוא עזב או איבד גישה ל-AI היא מושהית. הרצה שנכשלה מנסה שוב אחרי 15 דקות, משימה חוזרת שנכשלת 3 פעמים מושהית, והרצה שעברה את תקרת הקרדיטים מושהית. מגבלות: 10 משימות פעילות ב-AI בסיסי ו-50 ב-AI Pro. מנגנון ריצה ברקע (`POST /internal/jobs/tick`, נקרא כל 10 דקות מ-workflow ה-keep-awake, או `python -m app.jobs run-ai-tasks`) מריץ משימות שהגיע זמנן, ולכן השעה היא "בסביבות" עד שעובד בתשלום יקרא לו כל דקה (מסומן באפליקציה "בקרוב"). עדיין לא: התראה במייל או בפוש, RRULE מותאם, אישור אוטומטי לפעולות בסיכון נמוך. API‏ `/ai/tasks`, מיגרציה 0092.
- סוכנים יזומים: תדריך בוקר והצעות שבועיות (סבב 5, פרוסה A8): חלונית חדשה "צוות יזום" בדף צוות ה-AI (`/ai`), כבויה כברירת מחדל, למי שמנהל את צוות ה-AI (`ai.manage`). **תדריך בוקר:** כל יום בשעה שתבחרו (ברירת מחדל 07:30) אורי מסכם את הפגישות והשיעורים של היום, לידים חדשים או ממתינים והדברים הפתוחים שדורשים אתכם, בשפת העסק, בפחות מ-150 מילים, ומסיים בדבר הראשון שכדאי לעשות. **הצעות שבועיות** (מדליקים בנפרד, ברירת מחדל יום ראשון 08:00): אורי מחפש הזדמנויות (לקוחות שהפסיקו להגיע, שיעורים רחוקים ממלאים, לידים שאף אחד לא חזר אליהם, ירידה בהכנסות) ומכין עד שלוש הצעות ככרטיסים. שתיהן משימות מתוזמנות רגילות (A10) שנפתחות עבורכם, ולכן הן רצות בשמכם עם ההרשאות והסניפים שלכם כפי שהם היום, נספרות במגבלת המשימות של החבילה (10 ב-AI בסיסי, 50 ב-AI Pro) ובתקרות הקרדיטים (עד 10 ו-15 קרדיטים להרצה), הן לקריאה בלבד, וכל שינוי שהן מציעות הוא כרטיס שמחכה עד 3 ימים לאישורכם. כיבוי משהה את המשימה ושומר את ההיסטוריה שלה; הן מופיעות בלוח המשימות המתוזמנות ובהיסטוריית ההרצות עם השיחה שכל הרצה פתחה. עדיין לא: שליחה במייל או בפוש. API‏ `GET /ai/tasks/proactive`, ‏`PUT /ai/tasks/proactive/{key}`, מיגרציה 0096.
- **מיילים לעסק ולסניף (סבב 5, פרוסה F3).** בהגדרות יש עכשיו "מיילים של העסק", ובעמוד כל סניף "מיילים של הסניף": מייל ראשי, פניות, חשבוניות, מענה (Reply-To) והתראות (`contact_emails`, מיגרציה 0099). סניף בלי כתובת משלו משתמש בכתובת של העסק, ועסק בלי כתובת משתמש במייל ההתחברות של הבעלים. כתובת חדשה לא בשימוש עד שפותחים את הקישור שנשלח אליה (המייל של הבעלים עצמו לא צריך אישור). מיילים לצוות (פרסום סידור ושינויים) ולמתאמנים (התראות) יוצאים עכשיו בשם העסק עם Reply-To שלו, ומתאמנים רואים את המייל הראשי המאושר של הסניף ב-`/client/locations` (`contact_email`; מסך באפליקציה עוד לא נבנה). שליחה מהדומיין של העסק עצמו תבוא בהמשך (דורשת אימות דומיין).
- **דף צוות ה-AI (סבב 5, פרוסה A3).** הדף `/ai` (הכתובת הישנה `/assistant` מפנה אליו, וברשימת התפריט זה עכשיו "צוות AI") מציג את סוכני העסק על מפה מונפשת: המנהל הראשי באמצע, שאר הסוכנים סביבו, חלקיקים עדינים לאורך הקווים. יש גם תצוגת רשימה לטלפון, לקורא מסך ולמקלדת (חיצים מזיזים בין סוכנים, ובהעדפת "פחות תנועה" הכול נעצר). לחיצה על סוכן מזיזה את המפה בעדינות לצד ההתחלה (ימין בעברית) ופותחת שיחה מהצד השני, עם רצועה להחלפת סוכן, היסטוריית שיחות, שיחה חדשה ובורר סניפים (כל הסניפים או סניפים מסוימים; שינוי הבחירה פותח שיחה חדשה שממשיכה מהחלפת הדברים האחרונה). סוכן שהתוכנית לא כוללת, שכובה או שהתפקיד שלכם לא מורשה אליו מופיע כהה ונעול. לחיצה על נעול פותחת כרטיס שיווקי עם מחיר המודול וקישור "הוספה לתוכנית" (מי שאינו בעל העסק מתבקש לפנות אליו). עדיין לא: עריכת כרטיס סוכן ואשף "גיוס סוכן" (A4), העיגול הצף (A5), תשובות בסטרימינג (התשובה מופיעה כשהיא מוכנה), וקבוצות סניפים בבורר (G1).
- אין מקף ארוך בשום מקום (סבב 5, Q1): כל מקף ארוך ובינוני במסרים, באתר, באפליקציה, במיילים ובתיעוד הוחלף ב-"-". בדיקה ב-CI (`scripts/check-no-long-dash.cjs`) נכשלת אם הוא חוזר, ותשובות ה-AI מנוקות בשער ה-AI.
- **התנתקות מובילה לדף הבית (סבב 5, Q3).** התנתקות באתר פותחת עכשיו את דף הנחיתה עם הודעה "התנתקת בהצלחה" וכפתור "כניסה" בכותרת. פג תוקף ההתחברות עדיין מוביל לדף הכניסה וחוזר לאותו מסך אחריה. האפליקציות נשארות עם מסך הכניסה.
- **הודעות לפי סניף (סבב 5, פרוסה F4, מיגרציה 0101).** את ההודעה של העסק אפשר עכשיו לכוון לסניפים מסוימים (או לקבוצת סניפים) עם בורר הסניפים המשותף, ללקוחות או לעובדים, ובנוסף לוואטסאפ ול-SMS גם במייל, בהתראה באפליקציה ובחלון קופץ; ספירת הנמענים מתעדכנת חי לכל ערוץ. לקוח שייך לסניף לפי סניף הבית או רשימת "הסניפים שלי", עובד לפי רשימת הסניפים שלו (בעלים ומנהלים עובדים בכולם). מי ששייך לכמה סניפים בלבד מגיע רק אליהם. מייל, התראה וחלון קופץ עוברים במנוע ההפצה כהודעת עסק (שם השולח ו-Reply-To ממיילי העסק והסניף מ-F3); הודעה פרסומית נשלחת רק למי שאישר. לידים לא שייכים לסניף, לכן נשארים בטלפון בלבד ולכל הרשת.
- **מרכז הפצה (סבב 5, פרוסה M1, מיגרציה 0100).** בקונסולה של MyBiz יש עמוד חדש "הפצת הודעות" (הרשאה `broadcasts.manage`): כותבים הודעה בעברית ובאנגלית, בוחרים ערוצים (מייל, פוש, חלון קופץ בכניסה הבאה לאתר או לאפליקציה, וואטסאפ, SMS) וקהלים (צוות MyBiz, בעלי עסקים, עובדי עסקים, לקוחות העסקים; סינון לפי תחום, שפה, ניסיון או משלם, מודולים, עסקים ספציפיים), רואים ספירה חיה שבה אדם בכמה קהלים נספר פעם אחת, שולחים ניסיון לעצמכם, שולחים עכשיו או מתזמנים, וקוראים תוצאות (נשלח, נכשל, פתחו את החלון, לחצו, הסירו את עצמם). הודעה שיווקית מגיעה רק למי שאישר (הסכמה חדשה בחשבון וברשומות הלקוחות), מסומנת "פרסומת" בנושא ועם קישור הסרה חתום; הודעת שירות מגיעה לכולם. השליחה היא ג'וב שעתי חדש `send-announcements`; וואטסאפ ו-SMS עוברים בתור ההודעות של העסקים ונשארים מדומים עד שמחברים ספק בתשלום. פתיחות ולחיצות במייל לא נמדדות.
- **תמונות סוכני ה-AI (סבב 5, פרוסה A6).** תשעה פרצופים לסוכני ברירת המחדל, בצבע של כל סוכן, ועוד גלריה של שישה-עשר לסוכנים מותאמים, הכול באותו סגנון איור תלת-ממדי רך (WebP עם SVG גיבוי) ב-`packages/brand/agents`, שנוצרים בפקודה `pnpm --filter @business-os/brand build:agents`. בנוסף, ה-CI מוריד עכשיו את Postgres מהמראה של גוגל אחרי שהמראה של AWS התחילה להגביל.
- **פריסת ההרשמה וח.פ. (סבב 4, W5).** במסכים רחבים שלבי ההרשמה בעמודה בצד (ימין בעברית) ומתחתיה כרטיס "החבילה שלי" שנדבק בגלילה; בטלפון נשאר פס שלבים עליון קטן. בשלב פרטי העסק מבקשים ח.פ. / ת.ז.: חובה עם בדיקת ספרת ביקורת בעסק ישראלי (ש"ח), רשות בחו"ל, והוא נשמר בעסק אחרי ההרשמה.
- **פרופיל לקוח (סבב 3, פרוסה R8).** בפרופיל של הלקוח יש עכשיו תמונה עגולה (צילום או בחירה מהגלריה, חיתוך ריבועי, אפשר להסיר), השם וסטטוס חופשי קצר (עד 80 תווים, נשמר ב-`PATCH /me`). התמונה פרטית, ולכן האפליקציה מורידה אותה עם אסימון ההתחברות. נשען על `PUT/DELETE /me/avatar` הקיימים, בלי שינוי ב-API או בסכמה. שפה, ערכת צבע, גודל טקסט ו-Face ID כבר נמצאים בכרטיס ההעדפות שמתחת.
- **עיצוב חדש למיילים (סבב 4, פרוסה E1).** מעטפת אחת (`email_layout.py`) לכל המיילים, כולל מיילי ההתחברות של Supabase: כותרת עם גרדיאנט ולוגו, אייקון גדול לכל סוג מייל, כרטיס פרטים (שיעור, מועד) בהודעות הזמנה, מצב כהה ו-RTL. דף תצוגה מקדימה סטטי של כל המיילים בשתי השפות, בהיר וכהה, ב-`docs/email-preview/index.html`.
- **ליטוש טבלאות ותפריט נייד ב-CRM.** כל טבלאות הנתונים באפליקציית העסק ובקונסולה באותו מראה (שורת כותרת שקטה, קווים בין שורות, ריחוף עדין); מפת החום ולוח המשמרות פטורים. בטלפון יש קו מפריד בין התפריט לבר הכחול.
- **אפליקציה אחת בלבד (R13).** אפליקציות Expo הישנות של העסק ושל צוות MyBiz (`apps/business-app`, `apps/staff-app`) הוסרו: המסכים שלהן נמצאים ב-`apps/client-app`. CI, תהליכי הפריסה לווב ועדכוני EAS, מזהי החנויות והמסמכים מתייחסים עכשיו לאפליקציה האחת. הכתובות הישנות `mybiz-business-app` ו-`mybiz-staff-app` רק מפנות ל-`mybiz-client-app` (מריצים את *Deploy the Expo app to the web* עם *legacy-redirects*); פרויקטי Vercel ו-EAS לא נמחקו. שני סקריפטי ה-e2e של הטלפון הוסרו איתן; הבדיקה הסופית (R14) מכסה את אזורי העסק והצוות באפליקציה האחת.
- **מסך הבית של הלקוח לפי תחום (סבב 3, פרוסה R11).** הבית באפליקציית הלקוח הוא עכשיו רשימת כרטיסים שהתחום קובע (`client_home` בקטלוג, תתי-קטגוריות יורשות): ההזמנה הבאה עם ניווט, הוספה ליומן וביטול; מנוי או כניסות שנשארו; קיצורי הזמנה לשיעורים, תורים והשכרה; להזמין שוב; חיות או ילדים; הצהרת בריאות; מסמכים, הצעות וכתובות; עדכונים אחרונים; כתובות הסניפים. "ההזמנות שלי" מציג הזמנות קרובות ככרטיסים עם אותן פעולות, העדכונים מקובצים (היום, השבוע, קודם) עם אייקונים, וקביעת תור היא מסלול ממוספר עם סיכום וכפתור הוספה ליומן. ב-API: `home_cards` ב-`/client/businesses` ו-`GET /client/locations`. לא בפרוסה הזו: הרשמה לשיעורים (R9), השכרת מגרשים (R10), פרופיל (R8); שעות הפעילות של העסק דורשות הרשאת קריאה ללקוח.
- **סצנת פתיחה בתלת-ממד בדף הבית ומסך טעינה תלת-ממדי.** סצנה מעל הכותרת הראשית (יומן, לקוחות, תשלומים, הודעות, צוות ודוחות עפים פנימה ומתחברים סביב הלוגו; העכבר מטה אותה קלות) ומסך טעינה שבו הלוגו מתהפך כאריח תלת-ממדי בתוך טבעות מסתובבות. בלי ספרייה; בתנועה מופחתת מוצג המצב הסופי.
- **מסגרת כחולה אחידה ל-CRM ולקונסולה.** הבר העליון תואם עכשיו לתפריט הצד (Navy אחד, טוקן `--frame`) בבהיר ובכהה; הרקע מאחורי הכרטיסים באפור-כחלחל עדין בבהיר. צבע הסניף ממשיך לצבוע כפתורים ואת הפריט הפעיל בתפריט.
- **הצעות זמנים להשכרת מגרשים (API).** נקודת קצה חדשה עונה על "מתי נוח לך?": המגרשים הפנויים בדיוק בשעה המבוקשת, ועד 5 הצעות קרובות אחרות (מגרש אחד לכל שעת התחלה, באותו יום, ביום שלפני ובשני הימים שאחרי), עם הפרש הדקות מהשעה שביקשת. לקוח אחד למשבצת נשאר נאכף בהזמנה. מסך האפליקציה יגיע בחלק ההשכרה של סבב 3.
- אנימציות עדינות באתר וב-CRM: קטעי האתר נכנסים בעדינות בגלילה, כרטיסי התכונות בדף הבית מציגים חזותיות קטנות בלולאה, ורשימות ריקות ב-CRM מציגות איור מונפש קטן. הכול נעצר למי שמעדיף פחות תנועה.
- **API סבב 3: מאמן, פרסום שבועי וסטטוס.** שיעור מציג עכשיו את המאמן שלו (שם ותמונה, בלי אימייל) ואפשר לסנן לפי מאמן; עסק מציג שיעורים כמה ימים קדימה (ברירת מחדל 7) או פותח את השבוע הבא בכל שבוע ביום ובשעה שקבע, והצוות יכול לפרסם את השבוע הבא מוקדם יותר; הלקוח רואה מתי השבוע הבא נפתח. אפשר להגדיר בפרופיל סטטוס קצר (עד 80 תווים). מיגרציה 0080; שמונה ההחלטות של סבב 3 רשומות ביומן ההחלטות (X42-X49).
- **ניהול יומן (R12, סבב 3).** בלוח השיעורים יש כפתור "פרסום השבוע הבא", בהגדרות קובעים איך שיעורים נפתחים (כמה ימים קדימה או יום ושעה לפרסום שבועי), ובאפליקציית העסק אפשר לבטל או לשחזר שיעור שלם (הנרשמים מקבלים הודעה). צ'ק-אין והוספת לקוח לשיעור כבר היו במסך השיעור.
- **האפליקציות ב-Expo ובאתר מסונכרנות.** שלוש אפליקציות ה-Expo פורסמו מחדש (EAS Update, ענף `preview`) עם כתובות ה-API וה-Supabase של סביבת הבדיקה בתוך החבילה, מה שתיקן את השגיאה "משהו השתבש בשליחת הקוד (0)" בהתחברות; הקישורים של פרויקט EAS (כתובת העדכון, גרסת ריצה, מזהי חבילה) נשמרו עכשיו ב-`app.json` של כל אפליקציה. גרסאות הווב של האפליקציות, אתר השיווק וה-CRM נפרסו מחדש מאותה גרסה. פרסום ממחשב דורש `--environment preview` ואת שלושת ערכי `EXPO_PUBLIC_*`; תהליך "Publish Expo app updates (EAS Update)" ב-GitHub עושה את אותו הדבר.
- **ה-CRM בטלפון, מסודר.** כפתורי הכותרת (יומן, צוות) בנויים כרשת אחידה, בורר יום/שבוע/חודש ביומן בשורה משלו, שדות תאריך ושעה קומפקטיים במקום רחבים, והחלון "עובדים במשמרת" נפתח ליד המקום שנלחץ ונשאר כולו על המסך.
- **לוגו וצבע לכל סניף.** לכל סניף אפשר להגדיר לוגו וצבע משלו (בעמוד הסניף, למי שמנהל הגדרות); סניף שלא הגדיר מציג את אלה של הרשת. התפריט הצדדי מציג את הלוגו והצבע של הסניף הנבחר, ובסניפים עם לוגו משלהם הוא מופיע גם ברשימת הסניפים. API: העלאה ומחיקה של לוגו לסניף, צבע לסניף, ומיגרציה 0079. עוד לא באפליקציות Expo.
- אפליקציות: נעילה עם Face ID / טביעת אצבע. בכרטיס ההעדפות בשלוש האפליקציות יש מתג שנועל את האפליקציה בהפעלה ואחרי 30 שניות ברקע. Face ID באייפון דורש בנייה ייעודית (לא Expo Go). Passkey לא נבנה כי Supabase עדיין לא תומך בו.
- קודים של 6 ספרות וכניסה עם קוד: כל קוד שמגיע במייל (כניסה, אימות הרשמה, איפוס סיסמה) הוא עכשיו בן 6 ספרות במקום 8. חדש: באתר יש "כניסה עם קוד חד־פעמי", ובמסך הכניסה של שלוש האפליקציות בוחרים אם לקבל את הקוד במייל, ב-SMS או בוואטסאפ. המייל עובד כבר עכשיו. SMS ווואטסאפ בנויים (מאמתים את המספר פעם אחת בעמוד החשבון) ונשארים מוסתרים עד שמפעילים ספק בהשקה, כי הוא עולה כסף לכל הודעה.
- **לידים: בחירת עמודות להצגה.** תפריט "שלבים" עם תיבות סימון בלוח הלידים מציג רק את עמודות התהליך שנבחרו (חדש, נוצר קשר, ניסיון, הצעה, נסגר, אבד); עובד בטלפון, בעברית ובמצב כהה.
- **מסך פתיחה.** האתר, ה-CRM ושלוש האפליקציות נפתחים עם לוגו MyBiz מונפש קצר (קופץ פנימה, "נושם" ונעלם בעוד כשנייה וחצי) מעל הדף. הוא לא חוסם את הטעינה, באתר מופיע פעם אחת לכל סשן דפדפן, מתאים לבהיר/כהה, ובהפחתת תנועה מציג דהייה פשוטה וקצרה.
- אפליקציות בסגנון סבב 2: שלוש אפליקציות Expo עברו לפונט Assistant (כותרות אנגליות מודגשות ב-Plus Jakarta Sans כמו באתר), הודעות שמירה קופצות בתחתית המסך (הצעות מחיר, פניות, ניסיון עסק, פרופיל), כפתור שמש/ירח להחלפת מצב כהה/בהיר במסך הכניסה וליד בחירת המראה בכרטיס הפרופיל, ושדות אימייל, טלפון וקוד משמאל לימין; טלפונים ואימיילים בתוך משפט בעברית מבודדים ולא "קופצים" בתוך השורה.
- **כפתור נגישות: גרירה וסגירה.** אפשר לגרור את כפתור הנגישות הצף באתר ובמסכי ההתחברות לכל מקום (עכבר, מגע או חצים), הוא נשאר בתוך המסך וזוכר מיקום; איקס שחור קטן מסתיר אותו וקישור בפוטר מחזיר אותו.
- **מיילים מעוצבים.** כל המיילים חולקים עכשיו עיצוב אחד של MyBiz (כותרת כחולה כהה עם הלוגו, קוד גדול וברור, כפתור, מצב כהה, עברית מימין לשמאל ואנגלית): קוד כניסה, אימות הרשמה, איפוס סיסמה, הזמנה, שינוי כתובת, אישור זהות והתראות אבטחה (Supabase, עברית + אנגלית באותו מייל), וגם התראות ללקוחות, מיילי משמרות לצוות ומייל הפתיחה. הוראות הדבקה: `docs/deploy/auth-settings.md`.
- **הודעות שמירה ושגיאה ברורות.** הודעות "נשמר" ושגיאה מופיעות עכשיו כהודעה צפה צמודה לתחתית המסך (הצלחה 5 שניות, שגיאה 9, כפתור סגירה, נעצרת בריחוף, מעל חלונות, מצב בהיר/כהה, RTL, כיבוד הפחתת תנועה), במקום שורה בראש הטופס שנעלמה מהעין אחרי גלילה. כל הטפסים מקבלים זאת דרך `FormNotice` / `FormError`; שגיאות נשארות גם בתוך הטופס.
- **אפליקציות: העדפות נגישות.** בכרטיס ההעדפות בשלוש האפליקציות יש עכשיו גודל טקסט (רגיל / גדול / גדול מאוד), מתג להפחתת תנועה וניגודיות גבוהה. טקסט אנגלי מודגש ב-Plus Jakarta Sans כמו באתר, ועברית נשארת ב-Heebo.

- **תשובות AI בוואטסאפ, בנוי ומחכה (X37, פרוסה 8 לקראת העלייה).** עם התוסף *תשובות AI בוואטסאפ*, ה-AI עונה ללקוחות של העסק בוואטסאפ: אילו שיעורים יש, מה פנוי השבוע ומה ההזמנות שלהם. הוא אף פעם לא קובע לבד: הוא מציע מקום, והלקוח משיב 1 כדי לאשר; השרת (לא ה-AI) בודק שוב את ההצעה ואת כללי ההזמנה, קובע פעם אחת ורושם ביומן. למספרים לא מוכרים אין תשובה. שום דבר לא יוצא עד שמחברים ספק וואטסאפ אמיתי (ה-webhook סגור כל עוד הספק מדומה); ה-API כבר מציג את השיחות ומאפשר לעסק לנסות את הבוט בתור אחד הלקוחות בלי לשלוח ובלי לקבוע. מיגרציה 0078; משימת רקע `answer-whatsapp`.
- **ביקורת SQL שנבנה מ-f-string (H3).** נבדקו כל 107 הקריאות `text(f"...")` ב-API: נכנסים ל-SQL רק קבועים, תנאי WHERE שהקוד בוחר ושמות עמודות; ערכים תמיד עוברים כפרמטרים. `set_clause` מקבל עכשיו את רשימת העמודות המותרות (השדות של מודל ה-Pydantic של ה-endpoint) ודוחה כל מפתח אחר, וכך גם עדכוני החיוב, הצוות ושעות העבודה. בדיקה חדשה (`tests/test_sql_fstrings.py`) מכשילה את ה-CI כשמופיע f-string, `.format()` או `%` חדש בתוך `text(`
- **משימות הרקע במעקב.** כל הרצה של משימה נרשמת ב-`app.job_runs` (התחלה, סיום, הצליחה או נכשלה, תוצאה; מיגרציה 0075). `check-jobs` מתריע על משימה מתוזמנת שההצלחה האחרונה שלה ישנה מדי (יומיות: 27 שעות, שעתיות: 3 שעות); workflow יומי חדש `check-jobs-staging.yml` (06:23 UTC) מריץ אותה, ו-GitHub שולח מייל כשהיא נכשלת. `run-daily` / `run-hourly` מריצות כל קבוצה בפקודה אחת, עבור שירותי cron בפרודקשן, שמוגדרים ב-`render.yaml` אבל בהערה (כבויים) עד שתאשר פרודקשן.
- **מדיניות אבטחת תוכן (CSP) לאתר (H6).** כל עמוד מקבל עכשיו גם מדיניות קפדנית במצב דיווח בלבד: סקריפטים רצים רק עם קוד חד-פעמי (nonce) שנוצר לכל בקשה, חיבורים רק לאתר עצמו (הדפדפן לא פונה ישירות ל-API או ל-Supabase), בלי הטמעה באתרים אחרים ובלי תוספים. הדפדפן מדווח מה היה נחסם ל-`/api/csp-report`, שורת `csp-violation` לכל דיווח בלוגים של Vercel; בבדיקה בדפדפן העמודים הציבוריים לא הראו אף חסימה. המדיניות הישנה (שמתירה סקריפטים מוטמעים) נשארת באכיפה עד שהדיווחים נקיים, ואז הקפדנית מחליפה אותה (שורה אחת בקוד). נשלח גם HSTS לדומיין משלנו
- **"הצג עוד" ברשימות ארוכות (פרוסה 4 לקראת העלייה).** רשימת הלקוחות באפליקציית העסק והעדכונים באפליקציית הלקוח טוענים עמודים נוספים בלי תקרה; לוח הלידים באתר קיבל קישור "הצג עוד לידים" במקום לעצור ב-200. טבלת הלקוחות באתר כבר מחולקת לעמודים. להזמנות עדיין אין רשימה ב-API, ולכן אין מה לחלק.

- **CI לאפליקציות ובדיקת עומס (פרוסה 7).** שלוש אפליקציות הטלפון והחבילה המשותפת קיבלו lint ובדיקות ב-CI: כל מרחב הודעות שמסך מבקש חייב להתקיים בעברית ובאנגלית, וכל מסך חייב לייצא קומפוננטה. job חדש מזריע עסק דמו גדול פי 10 ומודד את שלושת המסעות העמוסים (היום, לקוחות, מספרים) מול תקציב של 2 שניות. הוא מצא שאילתה אחת איטית (לקוחות בסיכון, חיפוש נפרד לכל לקוח) ותוקן: מספרים 2.2 שנ׳ ל-1.1, היום 1.7 ל-0.5 בנפח פי 10. - **סגירת חשבון עסק ומחיקה אחרי 90 יום (P0-9, X20).** הבעלים סוגר את העסק ב-API (מקליד את שמו המדויק): העסק ננעל מיד לצוות וללקוחות, החיוב והתזכורות האוטומטיות נעצרים, ואפשר לפתוח מחדש במשך 90 יום. ה-job `delete-closed-businesses` מוחק אחר כך את העסק וכל נתוניו ורושם ביומן של MyBiz. בלי `--apply` הוא רק מדווח; ה-workflow היומי ב-staging מריץ אותו כדיווח, כך שהפעלת מחיקה אמיתית היא דגל אחד. הבעלים סוגר בהגדרות באתר או בלשונית "אני" באפליקציית העסק (מקליד את שם העסק), ועסק סגור פותח עמוד שבו הבעלים יכול לפתוח מחדש בתוך 90 הימים (שאר החברים מופנים לבעלים). הנוסח המשפטי אצל עורך הדין
- **הגדרות Auth של Supabase מ-CI (P0-8).** הסקריפט `supabase/apply_auth_settings.py` מחיל את חלק ה-auth של `config.toml` (אורך קוד, כתובות חזרה, תבניות מייל, סיסמאות) על הפרויקט; ה-workflow הידני *Apply Supabase auth settings (staging)* מציג קודם הבדלים ומשנה רק כשמסמנים apply. נדרש סוד אחד, `SUPABASE_ACCESS_TOKEN`, בסביבת staging ב-GitHub (אדיר: טוקן אישי מ-Supabase, פעם אחת)
